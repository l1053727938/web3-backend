# CEX 后端能力路线（交易 / 资产 / 账务 / 策略产品）

> 版本：v3（排期依据为"周容量假设 + 单元检查点"，不引用任何历史投入速率；主案 16 周）
> 唯一目标：**中心化交易所（CEX）后端**，对齐 JD1「核心交易链路：订单 / 账户资产 / 钱包账本 / 行情 / 用户平台」
> 与 JD3-4「交易类 + 资产类 + 产品类，至少两类实操经验」
> 基线：现有 web3-backend 已完成的链上出入金闭环（4 个模块 + 77 个离线单测 + 主网实跑对账），不再重复投入
> 时间口径：**按周容量假设排标准工期**（每周 14h 可用、只排 12h 计划量），主案 16 周，容量敏感性见 2.5

## 〇、本轮评审意见的采纳处置

评审提了 5 条补充、4 条压缩。**其中 3 条上一版路线已经覆盖（且落地层次比"学习理解"更深），2 条是本次新增采纳**：

| 评审建议 | 处置 | 落点 |
|---|---|---|
| 新增"账户资产模型"（现货/合约/资金分户、可用冻结总额三字段、余额表 vs 流水表） | **已在上一版**，本版细化为分户表结构 + 划转是分录对而非余额增减 | U1 |
| 复式记账做成小型账本 demo（表结构 + 几条 SQL） | **已在上一版**，且不止 demo：含借贷平衡应用层阻断、冲正规则、精度双轨 | U1 |
| "接口结果不确定"做成状态转换表 + 伪代码 | **已在上一版**，且有真实动机：广播超时留 `INIT` 锚点、替换失败不回拨 nonce、本机 Anvil 已撞出"hash 漂移无法自愈"的缺口 | U3 |
| 撮合边界加实操（跑开源 orderbook 观察 `MatchResult`） | **新增采纳**，但推荐自写 200 行 price-level + FIFO：跨语言读别人库的讲述收益低于自己动手 | U5 |
| "部分失败"场景覆盖不足（一笔清算多账户更新，部分成功怎么恢复） | **新增采纳**，独立列为专项 + 一组测试用例；JD1 原话，也是分布式事务取舍的正面回答 | U6 |
| 保证金与强平从半天拆两天，含强平触发计算 | **新增采纳**，扩为一个完整单元（持仓/保证金/强平/资金费率/ADL + 策略产品） | U7 |
| 分库分表不能只停在八股 | **新增采纳为"决策文档 + 实操"两段**，并点名一处与现有代码的真实冲突（见 U10） | U10 |
| JVM 排查、集成测试要在项目里真做一次 | **新增采纳**，从八股清单改为指定演练场景 + 留排查记录 | U10 |
| 交易域八股作为冲刺重点 | **新增采纳**，冲刺单元整段改为交易域 + 账务八股 | U11 |
| 压缩 Solana / SWAP / Foundry / Layer2 | **采纳但改变归置**：不分散塞进各单元（必被侵占），合并为机动缓冲包排最后 | 第十节 |

**定性**：评审要求"加厚交易域到 1.5-2 周"，本版给交易域 **3 个单元（U4 订单 / U5 撮合 / U6 清算）+ 1 个合约单元（U7）**，
净工时 56h，超过其要求量级；但**主干起点仍是账本（U1-U3）**——不是偏好，而是资金安全域是 JD1/JD3-4 的共同前置，且那是你唯一已有半条代码的域。

## 一、起点盘点：现有代码资产 ↔ JD 条款

这张表决定全部权重分配——已达标的绝不重复投入，缺的按单元补。

| JD 原话 | 现有实现证据 | 达标度 | 后续动作 |
|---|---|---|---|
| "业务状态流转" | `withdraw_record`：`INIT→BROADCAST→SUCCESS/FAILED/REPLACED`，跃迁全部走**带条件 UPDATE + 判 `updated>0`**（`markReverted`/`markAccelerated`/`markStuck` 带 `error_message IS NULL`） | ✅ | 整套模式迁移到订单状态机（U4） |
| "幂等" | `uk_chain_tx_log(chain_id,tx_hash,log_index)` + `INSERT IGNORE`；`uk_chain_wallet_nonce` 防重复提币；单号用 64bit 随机量防被 IGNORE 静默吞 | ✅ | 推广到订单/清算/账本分录 |
| "事务一致性" | 一页一事务（事件写入 + 游标推进同提交）；**空页不发 SQL 但照推游标** | ✅ | 账本要求更强：多分录同事务 + 平衡校验 |
| "消息可靠投递" | **先落库后 `PUBLISH deposit_channel`** + `notify_status(INIT/SENT/FAILED)` | 🟡 | Redis Pub/Sub 无持久化、订阅端离线即丢 → U2 换 outbox + Kafka |
| "失败补偿" | `notify_status=FAILED` 字段已留但**补偿器未实现**；RBF 提价重播；游标断点续拉 | 🟡 | U2 补 outbox 重发器；U1 补账本冲正 |
| "对账" | `/logs/transfer/saved-count` + 独立 RPC 直查比对（主网 USDT 16027 条实测对齐） | 🟡 仅雏形 | **U3 主攻** |
| "重复请求、超时、乱序、部分失败" | 重复=唯一键；超时=`rpc-segment` 指数退避+抖动、广播超时留 `INIT`；部分失败=路由异常不阻断主链路、单合约失败不中断整轮扫描 | 🟡 3/4 | **乱序未处理** → U2；**部分失败需专项** → U6 |
| "正确处理接口结果不确定……而非简单依赖重试" | 先落库 `INIT` 再广播；替换/撤销失败**一律不回拨 nonce 不改库**（与首广播相反）；终态门槛对 `SUCCESS`/`FAILED` 对称（防浅块 Revert 误判双花） | ✅ **最能打的一条，有实码有推导** | 面试直接讲门槛对称那条推演链 |
| "鉴权、超时、限频、重连" | JWT HS256 + 路径→scope；四道闸（全局/每用户速率/日配额/并发槽位）×LOCAL/DISTRIBUTED×FAST_FAIL/BOUNDED_QUEUE；`TransferStreamEngine` 指数退避重建整套连接 + newHeads 心跳判僵尸态 | ✅ | HMAC 落地 + scope 临时值 `test` 更正（U9） |
| "资金数据精度与安全意识（BigDecimal/定点数）" | 链上侧 `VARCHAR(78/80)` 存 `uint256` 十进制 + `decimals` 快照 + `displayValue` 换算 | ❌ **平台侧精度体系为零** | U1 与账本同时建 |
| "MySQL 表结构/索引/事务/锁/SQL 优化" | 6 张表、唯一键设计、`GREATEST` 单调游标 upsert、批量 1000 行、`idx_contract_block` 覆盖对账计数 | ✅ 无分片 | U10 分库分表 |
| "Redis、Kafka……消息重复、乱序、消费积压" | Redis 游标缓存降级、地址内存索引 + TTL、Redisson 锁/可过期信号量/分布式令牌桶 | ❌ Kafka 完全没有 | U2 |
| "性能测试与容量评估、慢 SQL、线程、JVM 排查" | 仅 Actuator + Prometheus | ❌ | U10 真做一次 |
| "单元测试和集成测试……配合联调提测上线" | 77 个离线单测（Mockito，不依赖节点/DB/Redis）+ 1 个需 Anvil 的集成测试 | 🟡 单测强集成弱 | U10 Testcontainers + CI |
| "微服务及 RPC 接口开发经验" / Dubbo、Nacos、K8s | 单体 + `Dockerfile` | ❌ | U10 |
| 加分项：撮合引擎、内存状态机、快照与日志恢复 | 无 | ❌ | U5 |
| 加分项：行情、盘口、K 线聚合、长连接推送、背压、慢消费者 | 只有 WS **客户端**经验 + 自研 `BoundedQueueRateLimiter`（双约束有界排队）/ `LeakyBucketRateLimiter`（匀速不放大突发） | 🟡 原语有、服务端无 | U8 |
| 产品类：网格、跟单 | 无 | ❌ | U7 后半 |
| 营销活动与 KYC/AML | 无 | ❌ | U9 |

**净结论**：资产类的**链上一半**已达标，**账本 / 对账 / 精度体系**设计有余而代码为零；**交易类、产品类、合规**基本空白。
路线因此把主干从"链"整体挪到"账 + 单"，链上能力降级为底座与差异化加分。

## 二、时间口径：标准排期（周容量假设 + 周级余量）

### 2.1 容量假设与排期原则

这一节只回答一个问题：**按正常投入，这条路线需要多久**。所有假设显式写出，不依赖任何"谁做得快"的推断。

**主案容量假设**：每周可投入 **14h**——平均每天 2h、每周 6 个有效日，外加约 2h 机动。这是"同时还有其它事务要处理"的常规强度，不是冲刺强度。

四条原则：

1. **计划量 ≤ 容量的 85%**：每周只排 **12h**，剩 2h 不预先分配给任何单元，专用于就地消化当周欠账。周级余量优于"单独设弹性周"——欠账在同一周内还掉，不需要重新起动机。
2. **最小粒度是单元，周只是容器**：单元可以跨周（U1、U3、U10 一定会跨），但每次重启单元必须写明"从哪个检查点接着走"。
3. **周次是容量承诺，检查点才是完成判据**。落后时不顺延单元、只顺延下游；连续两周欠账就按第十节第 4 条的砍法处理，不靠加班追回。
4. **验证与排障时间已含在单元工时里**（约 +20%），不另排期、也不留到最后补课。新域的返工率高于估算时的乐观假设，这是排期的一部分而不是意外。

| 单元 | 主题 | 类型 | 净工时 | 依赖 | 完成判据（检查点，过不了就不进下一个） |
|---|---|---|---|---|---|
| **U1** | 账户体系 + 复式账本基座 + 精度双轨 | 编码 | **18h** | 无 | 三表 DDL 落地；四场景分录各写平；借贷不平能阻断落库；"删余额表可由分录重建"验证通过 |

### 2.3 关键路径与并行机会

```
U1 ──┬── U2 ──── U3 ─┐
     ├── U4 ── U5 ── U6 ─┴── U8
     └── U7          U9 接 U1+U3
                    U10 接 U1-U6 全部
                    U11 → U12
```

- **U7（合约建模）与 U8（行情）可并行穿插**在 U4-U6 之后任意空档，因为它们不阻塞别人。
- **U11/U12 不要集中排到最后**：八股自测改为每单元结束时当场做一轮（每单元 +1h，已含在验证税里），最后只留简历与模拟面试。
- **U10 是最容易失控的单元**（四个新中间件），建议拆成 3 个子交付分开收口：分片决策 → Testcontainers+CI → JVM 排查与压测。

排布里刻意保留的四处结构：

- **每域收口后不立刻跨域**（W5/W10/W15 末尾只留回顾，不塞新单元）：账务与交易域的概念不掉一次成文复习就会在 U11 变成背八股。
- **U7 与 U8 可互换**：两者都不阻塞下游。若那段时间状态差，把建模单元（U7）提到前面，编码单元往后放。
- **U10 拆三周而不连续压成两周**：四个新中间件集中做完必然失控（第八节），三个子交付各自独立收口。
- **160h 内容 + 约 30h 回顾与间歇 = 16 周**。那 30h 不是留白，是新域必需的成文回顾时间；不排它，就会在第 10 周左右发现 U1 的分录规则已经记不清。

### 2.5 容量敏感性

同一份 160h 内容，在不同周容量下的日历长度。**不要按"多投入就线性缩短"外推**——每周计划量超过 16h 后边际收益明显下降，新概念的消化与返工不吃加班。

| 每周计划量 | 折算日历 | 适用前提与风险 |
|---|---|---|
| 8h（每天约 1.5h × 5 天） | **约 22 周** | 同时有全职或重度事务；风险是长战线使 U1 细节遗忘，M1 回顾要从 1 次加到 3 次 |
| **12h（主案，每周 14h 可用）** | **约 16 周** | 假设最稳妥，**对外承诺按这一档** |
| 16h（每天约 2.7h × 6 天） | **约 12 周** | 需要该阶段其它事务确实让位；U10 的三周拆分不可压成两周 |
| 20h（冲刺） | **约 10 周** | 只适合短期无其它负担；账务单元连续三周以上会显著掉速 |

若确实无法预估容量，按 8h 档排、按 12h 档执行：**提前完成的部分直接从缓冲包（第十一节）里取增量**，而不是把周次压短——路线的收益在单元质量里，不在日历长度里。

### 2.6 三个单元的负荷提示（不按平均节奏排）

- **U1 账本（18h）**：整条路线里唯一"写错就返工"的单元——复式分录、精度双轨、不变式都是第一次碰，瓶颈是概念正确性而非代码量。它跨 W1-W2 是**结构性的**，不是进度落后。
- **U6 部分失败恢复（14h）**：产出的一半是**取舍论证**（为什么不用分布式事务），要能自圆其说，不是写完回滚代码就过。
- **U10（26h）**：工具链上手 + 人为制造事故 + 定位，交付物是**两份排查记录和一份压测报告**，与编码单元完全不可比，所以它一定在最容易被打断的两周里被挤碎——放在最后、拆成三周。

## 三、U1 详解：账户体系与复式账本基座

### 3.1 分户模型（对应 JD1"账户资产"）

三个账户体系彼此隔离，**划转是账务动作、不是余额增减**：

```
资金账户（FUND，出入金/充提）
   ↕ 划转单（transfer_no，双向分录对）
现货交易账户（SPOT，按币种）
   ↕ 划转单
合约交易账户（PERP：全仓 CROSS 按币种挂保证金；逐仓 ISOLATED 按持仓位挂保证金）
```

- `account`：`(user_id, account_type, currency, available, frozen, total, version)` + `uk_user_type_currency`
- `account_transfer`：划转单（状态机 `INIT→SUBMITTED→SETTLED/FAILED`，幂等键 `uk(user_id, biz_type, biz_no)`）
- `perp_position`：持仓独立表（保证金模式、开仓均价、数量、标记价、维持保证金率、UPNL、强平价格）——**绝不允许塞进余额表**，否则余额更新要耦合价格推送。
- 不变式：`total = available + frozen`，用 CHECK/生成列 + 落库前应用校验双保险。

### 3.2 关键取舍（体例对齐 `docs/技术选型.md` 4.7）

| 取舍点 | 结论 | 理由 |
|---|---|---|
| 金额存哪 | **双轨**：链上侧继续 `VARCHAR` 存 `uint256` 十进制；账本侧一律 `DECIMAL(38,18)` + `BigDecimal` | 你已实测 `DECIMAL` 最大 65 位容不下 `uint256`（78 位），字符串写入不会因超大金额回滚整页；但账本要参与加减与平衡校验，字符串没有运算语义 |
| 换算时机与口径 | 只在"落账"这一步换算：`display = raw / 10^decimals`；账本 scale 取全部支持币种精度上界（ETH 18）；舍入方向全局唯一并显式定义 | USDT(6) 与 ETH(18) 混算必错；scale 低于任何币种精度就是丢钱。直击 JD"单位、精度、舍入、溢出" |
| 余额存不存 | 存（见 3.1），但必须满足"**删掉余额表、由分录重放能重建出相同余额**" | 这是"钱包账本"的真正不变量，也是面试判定题（原路线文档自测题 L307 已经问对了） |
| 冻结怎么记 | 冻结不是资金变动，是资金**属性**变动：`total` 不动，记 `available→frozen` 一对分录（同事务两条 posting） | 否则出现"冻结扣款"与"划转扣款"两套语义，对账无法解释差异 |
| 复式最小单元 | 一个业务动作 = 一组 posting，借贷必相等，平衡校验在应用层落库前阻断 | DB 触发器不可测、性能不可控、错误无法回传业务码 |
| 分录幂等 | `uk_biz(biz_type, biz_no)`，`biz_no` 取 `deposit_no`/`withdraw_no`/`match_id`/`transfer_no` | 与链上 `txHash+logIndex` 同族思路，且 `INSERT IGNORE` 重放安全已实测验证 |
| 余额并发 | `UPDATE ... SET available=?, version=version+1 WHERE user_id=? AND version=?`，失败**回滚整个业务事务**再重试 | 与 `wallet_nonce` 行锁单点分配同族；绝不允许无版本的"读-算-写" |
| 错账处置 | 分录**禁止 UPDATE/DELETE**，一律反向分录冲正，保留原分录与冲正关联 | 可审计性是账本立身之本 |

### 3.3 四类起步账户
`USER_SPOT`（用户现货）/ `USER_FROZEN`（用户冻结）/ `PLATFORM_FEE`（手续费收入）/ `SETTLE_PENDING`（待清算挂账）。
四个场景必须各写出一组平衡分录：**充值落账、下单冻结、成交清算（含手续费）、提币 FAILED 解冻退款**。写不出即账户分类缺项。

### 3.4 与现有代码的接点（不重写，只接）

| 现有位置 | 接什么 |
|---|---|
| `DepositRoutingServiceImpl` 第 3 步 `PUBLISH deposit_channel` | 改为同事务写 `outbox_message`，重发器投 Kafka；`notify_status` 语义原样沿用（本就是为补偿留的） |
| `deposit_record` 的 `PENDING_CONFIRM → CREDITED`（`技术选型.md` 待做项 2，尚未实现） | 确认推进器落账时同步产生充值分录；`INVALID` 作废产生反向分录 |
| `WithdrawTrackingServiceImpl#markReverted` 之后 | **FAILED 的解冻退款是账本侧第一笔真实业务动作**，也正是"终态门槛对称"这条设计的落地对象 |
| `transfer_event_log` | 对账的链上事实来源；`saved-count` 端点已是对账计数雏形 |
| `TokenMetadataService.decimals()` + 落库 `decimals` 快照 | 换算依据与事后追溯（快照而非回查链上，这个设计已经对了） |

## 四、U2-U3：消息可靠性、对账与"结果不确定"

### 4.1 U2 消息侧升级

| 现状问题 | 目标方案 | 验收 |
|---|---|---|
| Pub/Sub fire-and-forget，订阅端离线即永久丢 | 业务数据 + `outbox_message` **同事务**提交 → 轮询投递 Kafka → 标记 `SENT`；超限转人工 | 杀消费者 5 分钟，重启后不丢不重 |
| 无重投、无回溯 | 消息携带 `biz_no`，下游按 `biz_no` 幂等；分区键取 `user_id` | 重复投递不产生二次落账 |
| 乱序 | `user_id` 分区保序 + 业务版本号拒旧（Kafka 分区数与键的取舍要能讲） | 同一用户充值/冻结乱序到达仍能收敛 |
| 积压不可见 | 消费 lag 指标 + 告警 + 消费端并行度调优 | 人为压慢消费者能观测 lag 上涨并触发告警 |

### 4.2 U3 对账与锚点接管

- **三方逐项核对**：`transfer_event_log`（链上事实）vs `ledger_posting`（账本）vs `account`（余额快照）。
- **差异六类**：时间差（链上已确认平台未处理）/ 遗漏 / 重复 / 重组回滚 / 未知代币转入 / **精度差**。
  前五类通用对账教材都覆盖，**第六类只有自建账本才会暴露**（换算丢位、scale 不足、舍入方向不一致）——这是面试里能讲出"我做过"的硬证据。
- **处置分级**：时间差→下轮自动匹配；系统问题→修复后回填并留痕；资金异常→冻结通道 + 人工裁决。
  延续现有红线：作废 / 解冻带资金语义，**不能凭单次节点视图下结论**。
- **提币 `INIT` 锚点接管**（`技术选型.md` 待做项 4）：tracker 只扫 `BROADCAST`，广播超时留下的 `INIT` 行需按 `(from, nonce)` 判是否已上链再定终态。
  交付一张**状态转换表 + 伪代码**：`INIT` 悬挂 → 查 `(from,nonce)` 对应交易 → 三种结果（本笔上链 / 被同 nonce 他笔顶替 / 池内未上链）各自的处置与是否允许回拨 nonce。
  动机不是假想：本机 Anvil 真机排障已撞出"DB `transaction_hash` 漂移、按 hash 查不到收据但 nonce 已消耗，当前代码无法自愈"的实况。
- **调度直接复用**：`AutoBackfillScanner` 的双触发通道 + Redisson 全局 `tryLock` + "单合约失败不中断其余"，T+1 对账 Job 照抄。

## 五、U4-U6：交易域（订单 / 撮合 / 清算）

### U4 订单服务与状态机
- 状态机：`待提交 → 已提交(挂单中) → 部分成交 → 全成交 / 已撤单 / 失败 / 过期`；先画出**哪些是终态、每个跃迁的 WHERE 条件、可从哪些状态转到哪些状态**。
- **竞态解法直接迁移现有模式**：撤单与成交并发时用
  `UPDATE ... WHERE order_no=? AND status IN ('NEW','PARTIALLY_FILLED') AND version=?` 判影响行数——
  与现有 `markStuck`（带 `error_message IS NULL` 只标注一次）、`markAccelerated`（同 nonce 原地换 hash）是同一个模式。这条能讲出"不是从书上看来的"。
- 冻结差额退回：Taker 按自身报价冻结、按 Maker 价结算，差额回补 `available`（两条分录），对应自测题"100 挂买单 99 成交，1 USDT 去哪了"。
- 订单表与账户、账本的调用关系图（订单服务改状态、账本服务记分录，**跨服务不做强一致事务**，见 U6 部分失败）。

### U5 撮合边界
- 两条路径：**优先自写 200 行** price-level + FIFO 队列（价格优先、时间优先、限价单入簿/部分成交/撤单）；时间不足才用现成库跑一遍观察 `MatchResult`。选前者的理由：读 Go 库代码的讲述收益远低于自己写一遍 Java 版并画出数据结构。
- 必须能讲清的四点：为什么撮合通常**单线程/单写者**（同交易对多线程撮合的定序问题）、引擎**只产 `MatchResult` 不碰余额**（职责与恢复边界）、订单如何持久化与重启恢复（**快照 + 事件日志重放**）、`MatchResult` 的字段构成（takerOrder / makerOrder / price / qty / ts）。
- 自测：限价单挂进簿后价格未触及，它处于什么状态、冻结还在不在？撮合线程崩溃重启后内存订单簿如何与库中订单对平？

### U6 清算与部分失败
- `clearMatchResult`：Taker 冻结→Maker 可用；Maker 冻结→Taker 可用；手续费从成交所得扣（余额不足扣费的处理要能答）。
- **幂等**：同一 `match_id` 重复清算结果必须一致，靠 `uk_biz('MATCH', match_id)` + 分录组整体 `INSERT IGNORE`。
- **部分失败专项（JD1 原话）**：一笔清算涉及多账户多笔更新，两种边界分别怎么恢复——
  ① **同库同事务**（账本内部）：整体回滚 + 重试后仍平账，用 `@Transactional(rollbackFor = Exception.class)`；
  ② **跨服务**（订单已改状态、账本分录失败）：**不用分布式事务**，而是"账本为准 + `SETTLE_PENDING` 挂账 + 对账兜底 + 重试收敛"。
  这条取舍是面试必问，且与你现有代码哲学一致（路由异常不阻断主链路、缺失由补拉自然补齐）。
- 交付：四类单测用例（正常全成交 / 部分成交 / 重复清算 / 扣费余额不足）+ 一份 `clearMatchResult` 伪代码。

## 六、U7：合约持仓、保证金与强平 + 策略产品

评审要求"拆成两天"，本单元给 10h；不要求实现撮合与清算引擎，但**计算式必须能落到纸上**。

### 6.1 保证金与强平（前半）
- 概念定盘：标记价格（指数价 + 基差/资金费率调整，**不用最新成交价，防价格插针操纵**）、维持保证金率 MMR、初始保证金率 IMR、保证金率、UPNL。
- 逐仓 vs 全仓的差异要能算：逐仓强平只看本仓位保证金；全仓看账户权益（含所有 UPNL + 可用 + 冻结）能否覆盖总维持保证金。
- **强平价格计算式**（线性合约）：
  多头 \( P_{liq} = P_{entry} \times (1 - \frac{1}{L} + MMR) \)，空头 \( P_{liq} = P_{entry} \times (1 + \frac{1}{L} - MMR) \)，其中 \(L\) 为杠杆、\(MMR\) 为维持保证金率。
  用 10x + MMR 0.5% 实算一遍，验证强平距离与直觉一致（多头约在跌 9.5% 处）。
- 触发判定：`保证金余额 / 维持保证金 ≤ 1`（即保证金率 < 100%）；分级保证金（不同仓位规模对应不同 MMR）要能讲。
- 强平链路：强平订单进市场（或转保险基金/兜底仓）、**ADL 自动减仓**的顺序与选择依据。
- 资金费率：多空之间互换（平台不赚这笔、赚手续费与资金费抽成）、结算周期、正负号含义、作用是锚定永续价与现货价。
- 交付：一张"开仓→持仓→资金费结算→预警→强平/平仓"的状态流转图 + 保证金变化标注 + 保险基金与风险准备金的作用说明。

### 6.2 策略产品（后半，JD3-4"产品类"）
- **网格**：`策略单 → 档位配置 → 子单 → 成交 → 再平衡挂单`；停止时的结算语义（未成交批量撤单、已成交清算、套利收益折算）。
- **跟单**：跟随者资金**独立运行**（平台绝不代持资金池）、分润在策略停止时结算、杠杆与风险等级映射。
- 重点讲清两个边界：为什么策略引擎只下"订单"不碰"账本"；为什么跟单不能让主理人代持资金（账务与风控边界 + 挪用风险）。
- 交付：策略单/子单表设计 + 与订单服务、账本的调用关系图（不实现引擎）。

## 九、安全红线（贯穿全程）

沿用现有三条（来自卡单处置分层）：
1. 加速重播只允许"同 nonce + 完全相同的转账字段"，金额/收款人有一丝差异就是两笔提币。
2. 撤销空交易的哈希只写 `error_message`，**绝不覆盖 `transaction_hash`**，否则追踪会拿它成功收据误判 SUCCESS。
3. 未经确认数门槛的收据不得写任何终态（含 `FAILED`）——"钱没动"比"钱动了"安全这个直觉在账本上不成立。

账本侧新增五条：

4. 分录一经写入**不可 UPDATE / 不可 DELETE**，错账一律反向冲正。
5. 任何余额变动必须与分录**同事务**提交，不允许先改余额后补分录。
6. 借贷不平的分录组**拒绝落库**并视为资损级告警，不做任何自动修正。
7. 链上金额进账本必须按币种 `decimals` 换算并**留精度快照**；换算舍入方向全局唯一且有文档。
8. "作废 / 解冻 / 退款"这类带资金语义的动作，必须有可追溯的判定依据（确认数达标或三方对账结论），不接受单次节点视图作为终态理由。

## 十、执行原则与砍法

1. **资金安全 > 业务广度**：U1-U3 不许跳到 U4 之后，JD3-4 的原话就是"保障资金安全与数据一致性"。
2. **周次是容量承诺，检查点是完成判据**：以"检查点通过"为收口单位（见 2.2 最后一列），周历只约束投入上限（见 2.4）。检查点不过，宁可停在原单元也不推进——账务域的返工成本是跨单元的；落后只顺延下游，不顺延单元。
3. **每单元交付要能对着图讲 10 分钟**（沿用原文档自测口径）；单元结束时当场做一轮八股自测（计入验证税，不另排期）。
4. **进度落后的砍法**（按对 JD1/JD3-4 的贡献度从低到高砍）：
   先砍缓冲包全部 → 再砍 U7 后半（策略产品，JD 只要求"理解业务模型"）→ 再砍 U8 的 K 线聚合（保留推送与背压）→ 再砍 U5 的快照恢复（保留单写者与边界）
   → **U1-U3、U6 清算幂等与部分失败，不许砍**。
5. **不得用"看完教程"替代写代码**：U1/U2/U3/U4/U6 必须有可运行代码与单测；U5/U7/U9 允许只有设计文档 + demo。
6. **每两周回写一次 `docs/技术选型.md` 的"已完成/待做"两栏**，保持单一事实来源；本文件只维护单元状态三栏（已完成/进行中/未开始）。
