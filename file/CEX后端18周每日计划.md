核心目标：把"钱在系统里怎么表示"定死——三账户隔离、三张表、金额双轨制。本周不写业务，只建地基。

> **已交付**：

> - `MoneyUtils`：`toDisplay` / `toRaw` / `normalize`，舍入全局 `DOWN`，并拦截超出 `DECIMAL(38,18)` 容量的金额
> - `MoneyUtilsTest`：4 个单测全绿（USDT 6 位、ETH 1 wei、双向可逆、超精度截断）
> - 提交：`b64e8bb`（三表）→ `852f163`（CHECK）→ `62efff9`（MoneyUtils + 单测）
> **与计划的偏差**：
> - DDL 未拆成独立 `V1__account.sql`，统一维护在 `sql/schema.sql`
> - `CHECK` 加在生成列 `total` 上属恒真约束（`total` 由 `available + frozen` 自动生成），无法用「插入不平数据」验证；不平数据实际由生成列本身 + 应用层只改 `available/frozen` 拦截
> **纸笔产出（不在仓库）**：4 组分录、账户流转图 v1
> **下一周**：W2 四类分录、`post()`、余额重建与冲正

- **Day 1-2（3h）：[🔴 P1 死磕] 复式记账与分户模型（理论，只读 30 页）**
  - 会计恒等式：`资产 = 负债 + 所有者权益`；在 CEX 里落成"用户可用 + 用户冻结 = 用户总额"，平台侧对应"应付用户"。
  - 借贷必相等：一笔业务 = 一组分录（≥2 条 posting），`sum(debit) == sum(credit)`。**不是"一加一减"，是"有借必有贷"**。
  - 用 T 型账户手写 4 组分录，纸笔写，别用电脑：
    - 用户充值 100 USDT
    - 资金账户划 100 USDT 到现货账户
    - 下买单冻结 50 USDT
    - 成交后扣 1 USDT 手续费
  - 三大账户隔离：`FUND`（出入金）、`SPOT`（现货）、`PERP`（合约）。为什么合约账户不能和现货共用一张余额表——保证金率计算会把现货余额算进可用保证金，风控直接算错。
  - `perp_position` 为什么必须独立表：持仓有方向、杠杆、开仓价、保证金模式，塞进余额表就变成"余额带方向"，所有聚合查询全废。
  - 划转是账务动作：写一张 `account_transfer` + 一组分录（`FUND.available↓ / SPOT.available↑`），**不是** `update account set available = available - 100`。
  - 输出：账户流转图 v1（三个方框 + 双向箭头 + 划转单标注）。

- **Day 3-4（3h）：三张表 DDL**
  - `account`：`id / user_id / account_type / currency / available DECIMAL(38,18) / frozen DECIMAL(38,18) / total DECIMAL(38,18) GENERATED ALWAYS AS (available+frozen) STORED / version BIGINT / created_at / updated_at`。
  - 唯一键：`uk_user_type_currency (user_id, account_type, currency)`——一个用户一个币种一个账户类型只有一行，这是后续所有 CAS 的前提。
  - `account_transfer`：`transfer_no / from_account_id / to_account_id / currency / amount / status(INIT/SUCCESS/FAILED) / created_at`，`uk_transfer_no`。
  - `perp_position`：`id / user_id / symbol / side / qty / entry_price / margin / margin_mode(CROSS/ISOLATED) / leverage / version`，`uk_user_symbol_side_mode`。
  - 加 `CHECK (total = available + frozen)`。**注意版本**：MySQL 8.0.16 之前 `CHECK` 被解析但忽略，要真插一条 `available=1, frozen=1, total=999` 验证它到底拦不拦。
  - `version` 字段不是装饰：所有扣减走 `UPDATE ... WHERE id=? AND version=?`，影响行数为 0 就重试。

## 【第 2 周：账户体系与复式账本基座（二）】  ⬜

核心目标：`post()` 能拦住不平的分录；四个业务场景各写出一组平衡分录；**删掉余额表能重建**。

> **状态：⬜ 未开始 · 0%**

- **Day 1-2（3h）：[🔴 P1 死磕] 分录模型与"删表可重建"**（🔴-1 复式记账的落地延伸，"W1、W2 理论绝不偷懒"同此档）
  - 两张表：`ledger_entry`（分录组：`entry_no / biz_type / biz_no / status / created_at`，`uk_biz(biz_type,biz_no)`）+ `ledger_posting`（明细：`entry_id / account_id / direction(DEBIT/CREDIT) / amount / currency / balance_after`）。
  - 为什么分两张：一组分录是一个原子业务，`uk_biz` 放在组上才能做幂等；明细只管金额，条数不定。
  - `balance_after` 是可审计性来源：事后能回答"这笔操作之后余额是多少"，对账出差异时靠它定位。
  - 重建逻辑：`TRUNCATE account` → `SELECT account_id, SUM(CASE direction WHEN 'CREDIT' THEN amount ELSE -amount END) FROM ledger_posting GROUP BY account_id` → 与备份逐行 diff。
  - 这一步的意义：**证明你写的是账本，不是流水**。面试官问"删表能重建吗"，能当场说"能，我做过"。
  - 输出：两表 DDL + 重建 SQL。

- **Day 3-4（3h）：`post()` 实现**
  - 签名：`void post(LedgerGroup group)`，`LedgerGroup` 包含 `bizType / bizNo / List<Posting>`。
  - 五步，顺序不能换：
    1. 校验 `sum(DEBIT) == sum(CREDIT)`，不等直接抛 `UnbalancedLedgerException` + 资损告警（**不落库，不自动修正**）。
    2. 按 `(accountId)` 升序排序 posting（防死锁，两个事务交叉更新同一组账户必须同序）。
    3. 同事务内 `INSERT ledger_entry` → `INSERT ledger_posting`。
    4. 逐账户 `UPDATE account SET available=?, frozen=?, version=version+1 WHERE id=? AND version=?`，影响行数 0 则抛异常回滚整个事务。
    5. `@Transactional(rollbackFor = Exception.class)`，任何一步失败全组回滚。
  - 幂等：`INSERT ledger_entry` 命中 `uk_biz` 说明重复，直接返回原 entry，不再动余额。（机制本身属 🟡 P2：懂"唯一索引拦重复"即可，不追分布式一致性协议）
  - ➕ 连接池隔离（1h，本周余量）：账本 DB 用独立数据源（`ledgerDataSource` + `ledgerTransactionManager`，Hikari `maximumPoolSize=10` 独立于业务池）。理由：业务侧一条慢 SQL 把共享池占满时，`post()` 拿不到连接 → 充值/提币的余额变动全部卡死。`LedgerService` 显式绑定 ledger 事务管理器，别依赖默认的 `@Transactional`。
  - 输出：`LedgerService.post()` + 不平衡用例（断言抛异常且库中无记录）。

- **Day 5-6（4h）：四场景分录 + 冲正**
  - ① 充值落账：`USER.SPOT.available↑` / `PLATFORM_DEPOSIT_LIABILITY↓`（或对挂"平台待结算"），金额 = 链上到账额。
  - ② 下单冻结：`USER.SPOT.available↓` / `USER.SPOT.frozen↑`，`total` 不变。
  - ③ 成交清算：Taker `frozen↓`、Maker `available↑`，手续费单独一组 `USER.available↓ / PLATFORM_FEE↑`。
  - ④ 提币失败解冻：`frozen↓` / `available↑`，与②方向相反，`biz_no` 用原提币单号（天然幂等）。
  - 冲正：新增 `reverse_of` 指向原 entry，写一组方向相反的分录；**原分录永远不动**。
  - 禁止 UPDATE/DELETE：代码层拦截（`LedgerEntry` 无 setter）+ DB 账号只给 INSERT/SELECT（`ledger_posting` 不给 UPDATE 权限）。
  - 输出：4 组单测 + 冲正单测。

- **Day 7（2h）：自测 7 题 + 提交**

> **阶段产出**：`ledger_entry` / `ledger_posting` DDL + `LedgerService.post()` + 独立数据源 + 四场景分录 + 重建脚本 + 冲正流程。

## 【第 3 周：消息可靠性与 outbox】  🟡

核心目标：把现有"先落库再 `PUBLISH`"改成"业务 + outbox 同事务"；订阅端按 `biz_no` 幂等。这是"充值确认后通知账务"的可靠性基座。

> **状态：🟡 部分完成 · 约 30%**
> **已有**：先落库后发布（`DepositRoutingServiceImpl`）、`notify_status` INIT/SENT/FAILED 可观测、`uk_chain_tx_log` 幂等键
> **缺**：`outbox_message` 表与投递器、Kafka、消费幂等表（现为 Redis `PUBLISH`，无消费确认与重放）

- **Day 1-2（3h）：[🔴 P1 死磕：Outbox 原理 · 🟡 P2 理解：Kafka 概念] Kafka 概念 + outbox 表**
  - Kafka 四件事（🟡 P2）只取结论，不碰源码；Outbox 同事务与"至少一次必重复"的推理（🔴 P1）必须能脱稿讲。
  - 只搞清四件事：分区（同一 key 有序）、offset（消费者自己维护进度）、消费者组（同组内一条消息只被一个实例消费）、rebalance（会短暂停消费）。
  - "至少一次"意味着**一定会重复**，所以幂等不是优化，是前提。
  - 为什么不能"先发消息再落库"：消息发出去了、库回滚了，下游照着实不存在的订单结算 → 资损。
  - 为什么不能"先落库再发消息"（现有写法）：落库成功、进程在 `PUBLISH` 前挂掉 → 消息永久丢失，用户的充值永远不到账。
  - `outbox_message` 表：`id / biz_type / biz_no / payload JSON / status(NEW/SENT/FAILED) / retry_count / next_retry_at / created_at`，索引 `idx_status_next(status, next_retry_at)`。
  - 输出：DDL + 一页概念卡（分区/offset/组/rebalance 各一行）。

- **Day 3-4（3h）：改造充值链路**
  - 打开 `DepositRoutingServiceImpl`，把 `stringRedisTemplate.convertAndSend(...)`（现状是 Redis 发布，不是 Kafka）换成同事务 `outboxMapper.insert(...)`，`notify_status` 继续作为投递结果字段保留。
  - 关键：`@Transactional` 必须包住"业务表写入 + outbox 插入"，两者同生共死。写个单测：让业务抛异常，断言 outbox 里也没有记录。
  - 投递器：`SELECT * FROM outbox_message WHERE status='NEW' AND next_retry_at <= NOW() LIMIT 200 FOR UPDATE SKIP LOCKED`（防多实例抢同一条）。
  - 投递成功后 `status='SENT'`；失败 `retry_count+1`，按退避算 `next_retry_at`。
  - 输出：改造 commit + 单测（业务回滚则 outbox 为空）。

- **Day 5-6（4h）：消费者与本地跑通**
  - `docker compose` 起 Kafka（KRaft 单节点即可，别折腾 ZK）。
  - 消费者：`enable.auto.commit=false`，处理成功才 `ack.acknowledge()`。
  - 幂等表：`consumer_biz (biz_no VARCHAR PK, consumed_at)`，处理前 `INSERT` 命中主键冲突 → 直接 ack 跳过。
  - 端到端跑一次充值：**链上事件（WS 实时订阅与分页补拉两条入口，现成代码，见前置表）→ 落库 → outbox → Kafka → 消费者 → 账本分录**。本单元只验证链上入口与 outbox 的衔接，不改拉取逻辑。
  - 断一次 WS 再重连（现成 `TransferStreamEngine` 会自动退避重建），校验：不重复入账、不漏入账、`newHeads` 心跳能判出僵尸连接。
  - 输出：一条完整链路日志（截图关键三行）。

- **Day 7（2h）：风险表 + 自测**
  - 画一张表：消息丢了会怎样 / 重复会怎样 / 乱序会怎样，各自的兜底在哪。
  - 自测：为什么不能先发消息？消费成功但 commit 失败怎么办？分区键为什么选 `user_id`？

> **阶段产出**：`outbox_message` 表 + 投递器 + 幂等消费者 + 端到端跑通记录。
> **验收**：停掉投递器，业务照常落库（证明解耦）；手插两条同 `biz_no`，只落一次账。

- **Day 1-2（3h）：[🔴 P1 死磕] 退避重试与 DLQ**

  - 为什么要 jitter：所有实例的重试时间对齐，等于制造一次定时脉冲。
  - 超最大次数（建议 8 次）→ 写 `dlq_message` 表 + 告警，**不删原消息**。
  - 输出：`RetryPolicy` + 单测（断言 jitter 落在 `[0.5d, 1.5d]` 区间，跑 100 次不全相同）。

- **Day 3-4（3h）：失败补偿 + 杀消费者演练**
  - 🟡 `FAILED` 提币自动解冻（注意区分：现有 `notify_status=FAILED` 是通知失败，与提币失败无关）：复用 U1 第四场景，`biz_no = withdraw_no + '_REFUND'`，天然幂等。
  - 演练：`docker stop kafka`（或停消费者）5 分钟 → 期间继续产生充值 → 重启 → 校验：总条数一致、余额一致、重复落账数 = 0。

  - 输出：演练记录（处理前 N 条 / 重启后总数 / 重复数）。

- **Day 5-6（4h）：对账三方模型**
  - 三方：`transfer_event_log`（链上事实，由分页拉取 + 补拉兜底产出，现成代码）、`ledger_posting`（账本）、`account`（余额）。关联键 `biz_no = chain_id + tx_hash + log_index`。

- **Day 1-2（3h）：[🔴 P1 死磕] 差错六类与三类报表**

- **Day 5-6（4h）：INIT 锚点与分片并发**
  - `INIT` 三态判定（沿用现有 `WithdrawTrackingServiceImpl` 的 `INIT` 兜底逻辑（现状：tracker 只扫 `BROADCAST`，`INIT` 从未接管；三态规则见 `docs/技术选型.md` 待做 #4），改成"扫链真相"）：
    - 本笔 hash 已上链 → 补 SUCCESS；

## 【第 8 周：委托语义与订单状态机】  ⬜

核心目标：四种委托的冻结口径能列表；状态机画出终态与每个跃迁的 WHERE 条件；下单冻结链路跑通。

- **Day 1-2（3h）：[🟡 P2 理解] 委托语义**
  - 限价 GTC：挂簿等待，未成交部分一直冻结。
  - 限价 IOC：立即成交可成交部分，剩余**立即撤销**并解冻。
  - 限价 FOK：要么全部成交，要么整单撤销——**永不进入部分成交状态**。
  - 市价：无报价，按"对手盘深度累加 + 滑点上限"冻结，深度不足直接拒单。
  - 做一张四行表：委托类型 / 冻结金额算法 / 是否可部分成交 / 剩余处理。
  - 输出：四行对照表。

- **Day 3-4（3h）：状态机与订单表**
  - 状态：`PENDING_SUBMIT → NEW → PARTIALLY_FILLED → FILLED / CANCELED / REJECTED / EXPIRED`。终态四个，终态不可再跃迁。
  - `order` 表：`order_no / user_id / client_order_id / symbol / side / type / tif / price / qty / filled_qty / frozen_amount / status / version`，`uk_user_client(user_id, client_order_id)`、`uk_order_no`。
  - 为什么 `client_order_id` 的唯一键必须带 `user_id`：不同用户可能用同一个客户端单号，全局唯一会误伤。
  - 输出：状态机图 + DDL + 跃迁条件表（每个跃迁写 `WHERE status IN (...) AND version=?`）。

- **Day 5-6（4h）：下单链路**
  - 顺序：参数校验 → 冻结（调 `LedgerService.post`）→ 落单（`status=NEW`）→ 返回。
  - 冻结失败（余额不足）→ 直接拒单，不落库（或落 `REJECTED` 用于审计，二者选一并写进文档）。
  - 注意：冻结与落单必须同事务，否则"冻结成功、落单失败"会留下孤儿冻结，只能靠对账捞。

## 【第 9 周：竞态、差额退回与客户端幂等】  ⬜

核心目标：并发撤单与成交不重复释放冻结；差额退回两条分录正确；`client_order_id` 重放返回原单；订单簿能入簿与部分成交。

> **状态：⬜ 未开始 · 约 5%**
> **可复用**：条件更新判影响行数的习惯（`uk_chain_wallet_nonce` 下原地换 hash 就是同一手法）
> **缺**：撤单/成交 CAS 压测、差额退回、`client_order_id` 幂等、订单簿

- **Day 1-2（3h）：竞态 CAS**
  - 撤单：`UPDATE orders SET status='CANCELED', version=version+1 WHERE order_no=? AND status IN ('NEW','PARTIALLY_FILLED') AND version=?`，影响行数 0 → 说明已被成交抢先，放弃撤单。
  - 成交：同样条件更新到 `PARTIALLY_FILLED` / `FILLED`，影响行数 0 → 说明已被撤单，回滚清算。
  - **为什么不引入全局序列号**：撮合是单写者，已经给出了全序；账户侧再加一个序列号是重复定序，还多一个单点。
  - 压测：100 线程同时撤单 + 成交，校验冻结释放次数 = 1。
  - 输出：压测脚本 + 结果。

- **Day 3-4（3h）：[🔴 P1 死磕] 差额退回 + 幂等**

  - 为什么两条而不是一条 `UPDATE`：差额必须可审计，对账要能解释"为什么冻结了 100 只花了 99"。
  - `client_order_id` 幂等：入口先查 `uk_user_client`，命中直接返回原单（HTTP 200 + 原 `order_no`），**不报错**。连点、网关重试都是合法重放。
  - 输出：退回分录 + 单测 + 幂等重放单测。

## 【第 10 周：撮合边界与清算幂等】  ⬜

核心目标：订单簿能跑出部分成交与撤单；能讲清"引擎不碰余额"；`clearMatchResult` 幂等。

> **状态：⬜ 未开始 · 0%**
> **可复用**：业务唯一键做幂等的思路（可套到 `match_id`）
> **缺**：订单簿、`MatchResult`、`clearMatchResult`、快照恢复设计

- **Day 1-2（3h）：[🟡 P2 理解] 订单簿收尾 + 职责边界**
  - 本日理论（单写者论证、恢复边界）属 🟡 P2：明白"为什么单线程最快""引擎为什么不碰余额"即可，不必真写 LMAX 级无锁队列；撤单补齐与代码产出仍是本周硬任务。
  - 补撤单（从队列中移除，注意 `ArrayDeque.remove` 是 O(n)，200 行版本可接受）。
  - `MatchResult` **不含任何余额字段**——这是职责边界，也是恢复边界：引擎崩了只需重建订单簿，不用回滚账。
  - 快照 + 事件日志重放：每 N 笔成交流一次快照，重启 = 加载快照 + 重放增量。只做设计不实现，但要能讲"恢复边界在哪"。
  - 单写者论证：同交易对多线程撮合会产生"同一价格两个线程同时吃同一档"的定序问题，加锁不如单线程。
  - 输出：完成代码 + 一页设计。

- **Day 3-4（3h）：清算主体**
  - `clearMatchResult(MatchResult)`：Taker 的 `frozen` 扣减 → Maker 的 `available` 增加 → 手续费从成交所得扣。
  - 买卖双向都要覆盖：Taker 买 / Maker 卖、Taker 卖 / Maker 买，四条路径。
  - 手续费：从买方所得或卖方所得扣，取决于币种（现货通常是扣所得币种）。
  - 输出：核心实现 + 双向用例。

- **Day 5-6（4h）：幂等与单测**
  - 幂等键：`uk_biz('MATCH', match_id)`，`match_id` 由 `taker_order_id + maker_order_id + seq` 组成。
