# 账本连接池隔离（ledgerDataSource / ledgerTransactionManager）

> 对应 18 周计划第 2 周 Day 3-4 的「➕ 连接池隔离」
> 目标：业务侧慢 SQL 或流量尖峰占满业务池时，`post()` 仍能拿到连接，充值/提币的余额变动不被连坐
> 产出：独立 Hikari 池 + 独立 SqlSessionFactory + 独立事务管理器，并已验证应用可正常启动

---

## 一、要解决的问题

账本是资金链路。共用连接池时的故障传导：

```
业务慢 SQL / 批量入库 → 业务池 20 个连接被占满
                              ↓
        post() 调用 getConnection() 阻塞 30s → Timeout
                              ↓
              充值、提币的余额变动全部卡死
```

切断这条传导链，只需要把「账本拿到的连接」和「业务拿到的连接」分到两个池里。

注意：默认方案是**同一个 MySQL 库、两个连接池**，隔离的是「连接」不是「数据」。
以后要物理分库，只改 `spring.datasource.ledger.jdbc-url` 即可，代码零改动。

---

## 二、实现结构

```
src/main/java/com/ray/web3/
├── config/
│   ├── DataSourceConfig.java         业务池：dataSource / sqlSessionFactory / sqlSessionTemplate / transactionManager（全 @Primary）
│   ├── LedgerDataSourceConfig.java   账本池：ledgerDataSource / ledgerSqlSessionFactory / ledgerSqlSessionTemplate / ledgerTransactionManager
│   └── MybatisFactorySupport.java    两个池共用的 SqlSessionFactory 构造，避免行为漂移
├── ledger/mapper/                    账本 Mapper（AccountMapper / LedgerEntryMapper / LedgerPostingMapper）
└── mapper/                           业务 Mapper（其余全部）
```

路由规则只有一条：**Mapper 在哪个包，就走哪个池**。

| 包 | SqlSessionFactory | 连接池 |
|---|---|---|
| `com.ray.web3.mapper` | `sqlSessionFactory` | 业务池（20） |
| `com.ray.web3.ledger.mapper` | `ledgerSqlSessionFactory` | 账本池（10） |

---

## 三、为什么必须显式声明主池的四件套

这不是「加一个 DataSource 就行」，而是三处 `@ConditionalOnMissingBean` 连环退让：

| 自动配置 | 退让条件 | 只加账本 Bean 的后果 |
|---|---|---|
| `DataSourceAutoConfiguration.PooledDataSourceConfiguration` | 缺 `DataSource` | 业务 `DataSource` 不再创建 |
| MyBatis-Plus `sqlSessionFactory` / `sqlSessionTemplate` | 缺同类型 Bean | 业务工厂、模板不再创建 |
| `DataSourceTransactionManagerAutoConfiguration.transactionManager` | 缺 `TransactionManager` | 默认事务管理器不再创建 |

所以 `DataSourceConfig` 里主池的 `dataSource`、`sqlSessionFactory`、`sqlSessionTemplate`、`transactionManager` 必须全部手写，并用 `@Primary` 标记。

## 四、关键代码

### 4.1 业务池（主池）

```java
@Configuration
public class DataSourceConfig {

    @Bean
    @Primary
    @ConfigurationProperties("spring.datasource.hikari")
    public HikariDataSource dataSource(DataSourceProperties properties) {
        return properties.initializeDataSourceBuilder()
                .type(HikariDataSource.class)
                .build();
    }

    @Bean
    @Primary
    public SqlSessionFactory sqlSessionFactory(@Qualifier("dataSource") DataSource dataSource) throws Exception {
        return MybatisFactorySupport.build(dataSource);
    }

    @Bean
    @Primary
    public SqlSessionTemplate sqlSessionTemplate(@Qualifier("sqlSessionFactory") SqlSessionFactory factory) {
        return new SqlSessionTemplate(factory);
    }

    @Bean
    @Primary
    public DataSourceTransactionManager transactionManager(@Qualifier("dataSource") DataSource dataSource) {
        return new DataSourceTransactionManager(dataSource);
    }
}
```

### 4.2 账本池

```java
@Configuration
@MapperScan(basePackages = "com.ray.web3.ledger.mapper",
            sqlSessionFactoryRef = "ledgerSqlSessionFactory")
public class LedgerDataSourceConfig {

    @Bean
    @ConfigurationProperties("spring.datasource.ledger")
    public HikariDataSource ledgerDataSource() {
        return new HikariDataSource();
    }

    @Bean
    public SqlSessionFactory ledgerSqlSessionFactory(
            @Qualifier("ledgerDataSource") DataSource ledgerDataSource) throws Exception {
        return MybatisFactorySupport.build(ledgerDataSource);
    }

    @Bean
    public SqlSessionTemplate ledgerSqlSessionTemplate(
            @Qualifier("ledgerSqlSessionFactory") SqlSessionFactory factory) {
        return new SqlSessionTemplate(factory);
    }

    @Bean
    public DataSourceTransactionManager ledgerTransactionManager(
            @Qualifier("ledgerDataSource") DataSource ledgerDataSource) {
        return new DataSourceTransactionManager(ledgerDataSource);
    }
}
```

### 4.3 服务层显式绑定事务管理器

```java
@Override
@Transactional(transactionManager = "ledgerTransactionManager", rollbackFor = Exception.class)
public LedgerEntry post(LedgerGroup group) { ... }
```

不写 `transactionManager` 就会落到主池的事务管理器上，出现「账本 SQL 在账本连接上、事务锁在业务连接上」的错乱。

### 4.4 配置

```yaml
spring:
  datasource:
    hikari:                      # 业务池
      maximum-pool-size: 20
      ...
    ledger:                      # 账本池
      jdbc-url: jdbc:mysql://.../web3_backend?...
      username: ${MYSQL_LEDGER_USERNAME:${MYSQL_USERNAME:root}}
      password: ${MYSQL_LEDGER_PASSWORD:${MYSQL_PASSWORD:123456}}
      driver-class-name: com.mysql.cj.jdbc.Driver
      pool-name: ledger-pool
      maximum-pool-size: 10
      minimum-idle: 2
      connection-timeout: 5000   # 比业务池短，宁可快速失败让调用方重试
      ...
```

## 五、优点

1. **故障隔离（核心收益）**
   业务池被打满时，账本池仍有连接，`post()` 不会因为业务慢查询而超时；反过来账本大事务也吃不掉业务池。

2. **两池按各自负载调参**
   账本：小池、短取连接超时（失败快、重试快）；业务：大池、长超时。共用池时只能取折中值。

3. **事务边界显式化**
   `transactionManager = "ledgerTransactionManager"` 写死后，账本 SQL 与账本事务锁必然在同一个池的连接上，消除了「选错事务管理器」这类只在高并发才暴露的隐性错误。

4. **为物理分库留口子**
   未来把 `jdbc-url` 指向另一个实例即可，业务代码不用改。

5. **可观测性更好**
   两个池各自暴露 Hikari 指标（活跃连接、等待时间、超时次数）。账本池出现 `connectionTimeout` 就是「记账堆积」的早期信号。

---

## 六、缺点与风险

1. **要手工重建 Spring Boot 自动配置**
   主池四件套都得自己声明，等于替 Boot 干活；Boot 升级时这些代码不会自动跟着演进。

2. **配置存在双份，容易漂移**
   - JDBC URL 在 yml 里写了两遍（靠占位符默认指向同一库）；
   - `MybatisFactorySupport` 手写了 `mybatis-plus.*` 的等价配置（下划线转驼峰、SQL 日志、主键自增）。
   改了 yml 不同步改 Java，就会出现两池行为不一致，且不易发现。
   **改进方向**：两个工厂都从 `MybatisPlusProperties` 读取配置，只保留数据源差异。

3. **Mapper 路由靠包名，是「沉默故障」**
   把 `AccountMapper` 挪回 `com.ray.web3.mapper`，编译通过、单测通过（Mock 的），线上却悄悄走业务池，隔离失效且无任何报错。
   **改进方向**：加启动自检或 ArchUnit 规则，断言 `com.ray.web3.ledger.mapper` 下的接口都绑定 `ledgerSqlSessionFactory`。

4. **总连接数翻倍**
   每实例 20 + 10 = 30。3 个副本就是 90，要确认 MySQL `max_connections` 扛得住，否则「隔离」只是把排队从应用搬到了数据库。

5. **跨池不能原子（最重要）**
   两个事务管理器 = 两条连接 = 两个独立事务。在业务 `@Transactional` 内调用 `post()`，两者不会一起回滚。
   **资金链路的跨域一致性必须走 outbox / 事件驱动最终一致**，不能假设跨池原子。

6. **隔离的是连接，不是数据库**
   共用 MySQL 实例时，CPU、IOPS、行锁、DDL 元数据锁、大事务的 undo 压力仍然互相影响。真要做到资源级隔离，最终要物理分库/分实例。

7. **复杂度提前支付**
   单实例、低流量、账本和业务都不慢时，这套隔离的收益接近 0，却多了三份配置和一类排查路径。

---

## 七、方案对比

| 方案 | 隔离效果 | 复杂度 | 跨域事务 | 适用阶段 |
|---|---|---|---|---|
| 共用一个池 | 无 | 低 | 同一事务 | 业务未跑通、单实例 |
| **同库两个池（当前）** | 连接级 | 中 | 不可跨池 | 资金链路延迟敏感、已有慢 SQL 风险 |
| 独立库/实例 | 资源级 | 高 | 不可跨库，需 outbox | 生产多副本、账本独立演进 |

---

## 八、落地建议

1. 两个 SqlSessionFactory 改为读 `MybatisPlusProperties`，消除配置双份；
2. 加启动自检 / ArchUnit 测试，锁住「账本 Mapper 必须在 `com.ray.web3.ledger.mapper`」；
3. 在 `post()` 注释中明确写死：**禁止在业务 `@Transactional` 内调用，跨域一致性走 outbox**；
4. 监控两个池的 Hikari 指标，对账本池的 `connectionTimeout` 单独告警。

## 十、一句话总结

**隔离换来的是「账本不被业务拖死」，代价是「跨池不能原子 + 配置双份 + 路由靠包名的沉默风险」。**
对本项目而言收益明确、值得保留，但必须把 outbox 边界和 Mapper 包归属写进规范，否则隔离会在某次重构后静默失效。
