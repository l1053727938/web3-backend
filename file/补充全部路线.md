## 四、第二阶段：交易域业务模型 + 非 EVM 链（第 4-5.5 周）

### 第 4 周：交易域核心业务模型（新增，权重最高）

> JD 中"订单匹配与清算""现货/合约交易引擎""持仓/保证金""网格/跟单"是反复出现的硬性要求，原计划完全缺失。

- 订单模型：限价/市价、订单状态机（待成交/部分成交/全成交/撤单/失败）、冻结/解冻
- 撮合基础：价格优先时间优先、撮合引擎与账户系统的边界（为什么撮合内存化、订单如何落地）
- 清算流程：成交回报 → 资金划转 → 账本记账，T+0 清算数据流
- 合约基础：保证金、逐仓/全仓、强平逻辑、资金费率概念
- 网格/跟单：策略单 → 子单 → 成交的状态流转（理解业务模型即可，不要求实现）
- **交付验证**：能画出"下单 → 撮合 → 成交 → 清算 → 账本"的完整数据流和一致性方案
- 逐日任务见[专题一](#八专题一第-4-周交易域核心业务模型逐日清单)

### 第 5 周：Solana 核心架构（压缩为概念对比 + 监听 demo）

- 理论：Account 模型（数据与代码分离）、PDA、Instruction 机制 vs EVM 合约调用
- 工具：@solana/web3.js

### 第 5.5 周（3-4 天）：分布式一致性与消息可靠性专题（新增）

> JD 原话："正确处理接口结果不确定、服务中断及异步处理失败，而非简单依赖重试""消息可靠投递、失败补偿与对账""乱序、部分失败"。

- 本地消息表方案：消息表与业务数据同事务提交，定时轮询重试，超限后批量补偿核对
- 消息乱序处理：按订单号/账户号分区、版本号/序号去重
- 接口结果不确定：超时后查单、状态机幂等、防重复提币的"先落库后调用"
- Kafka 消费幂等：发送时传入唯一流水号，消费端判断是否已消费
- 消费积压定位：消费速度跟不上、消费端阻塞、同步等待远程调用超时处理
- 逐日任务见[专题二](#九专题二第-55-周分布式一致性与消息可靠性逐日清单)

## 八、专题一：第 4 周交易域核心业务模型逐日清单

> 目标：能画出"下单→冻结→撮合→清算→账本"完整数据流，讲清各服务边界与一致性方案。不要求写撮合引擎。

### Day 1：订单模型与状态机

**学习内容**
- 订单类型：限价单/市价单，Maker/Taker 区别，订单有效期（DAY/GTC/IOC/FOK）
- 订单状态机：待提交→已提交（挂单中）→部分成交→全成交/已撤单/失败/过期
- 冻结/解冻时机：下单时冻结什么、成交时解冻多少、撤单时释放多少
- 关键细节：Taker 买入时按 Maker 价格成交，冻结按 Taker 报价，差额需退回

**必读/参考方向**
- 廖雪峰《设计清算系统》：冻结与差额退回的具体逻辑
- Coinbase 架构文档中"Priority and cancellation"部分：序列号与取消的竞态处理

**自测问题**
1. 用户以 100 USDT 挂买单，Maker 以 99 USDT 成交，冻结的 1 USDT 差额如何处理？
2. 撤单请求和成交同时到达，系统应如何保证不重复释放冻结？
3. 订单状态机中哪些状态是终态？哪些可以转换到哪些状态？

**交付**：画出订单状态机图（含冻结/解冻标注）。

### Day 2：撮合基础与引擎边界

**学习内容**
- 价格优先、时间优先规则；价格档位（price level）与 FIFO 队列
- 撮合引擎的内存化原因：低延迟、避免数据库往返
- 撮合引擎与账户系统的边界：引擎只产出"成交结果"，不清算资金
- 单写者模型（LMAX 风格）：为什么撮合线程是单线程的，命令如何排队
- 撮合结果的数据结构：MatchResult 包含 takerOrder、makerOrder、成交价量

**必读/参考方向**
- Go orderbook 库文档中 Runner/MatchResult 的设计说明
- Velocity CEX 开源项目的架构描述：MPSC 通道、内存订单簿、事件发射

**自测问题**
1. 为什么撮合引擎通常单线程处理一个交易对？多线程撮合同一交易对会有什么问题？
2. 撮合引擎输出成交结果后，谁负责扣款/入账？为什么不让引擎直接改余额？
3. 限价单进入订单簿后，如果价格未触及，它处于什么状态？冻结还在吗？

**交付**：画出"订单进入引擎→撮合→输出 MatchResult"的流程，标注内存与持久化的分界。

### Day 3：清算流程与资金划转

**学习内容**
- 清算的定位：撮合产出成交结果后，完成买卖双方资产交换
- 清算核心操作：Taker 冻结资产 → Maker 可用资产；Maker 冻结资产 → Taker 可用资产
- 手续费处理：从哪一方扣、扣什么资产、在清算的哪个步骤扣
- 清算与账本的关系：清算是业务动作，账本是记录方式（Day 4 展开）
- 幂等要求：同一 MatchResult 重复清算必须结果一致

**必读/参考方向**
- 廖雪峰清算代码框架：`clearMatchResult` 的 BUY/SELL 分支逻辑
- Coinbase 架构中"每个成交消耗订单预留、转移资产、记录费用"的描述

**自测问题**
1. 一笔 Taker 买单部分成交了两笔 Maker 卖单，清算时资产转移的顺序和金额分别是什么？
2. 如果清算过程中数据库写入失败，系统如何恢复到一致状态？
3. 手续费在清算时扣除，如果用户可用余额不足扣手续费怎么办？（提示：从成交所得中扣）

**交付**：用伪代码写出 `clearMatchResult` 的核心逻辑（Taker BUY 场景）。

### Day 4：复式记账账本模型

**学习内容**
- 为什么交易表 ≠ 账本：交易表记录状态变化，账本记录资金流动且不可变
- 复式记账核心不变量：每笔分录借方总额 = 贷方总额
- 账户分类：资产/负债/收入/费用，各自借贷方向
- 账本设计在交易所的落地：用户可用账户、冻结账户、平台手续费收入账户、平台冷钱包账户
- 余额推导：账户余额 = 重放所有分录得出，而非直接更新字段

**必读/参考方向**
- Dodo Payments 支付账本设计：复式记账的运行时约束、守恒性、可审计性
- Formance 交易所账本方案：每一笔成交、费用都是账本上的 posting

**自测问题**
1. 用户充值 100 USDT，用复式记账写出分录（涉及哪些账户？借贷各是什么？）
2. 用户下单冻结 50 USDT，写出分录。成交后清算时又该如何记？
3. 为什么说"如果删除账本再根据交易表重建，能得到相同余额，才算真账本"？你的资产网关项目能做到吗？

**交付**：为资产网关的充值/冻结/成交/提币四个场景各写一组复式分录。

### Day 5：合约基础 + 网格/跟单业务模型

**学习内容**
- 永续合约核心概念：保证金（逐仓/全仓）、强平、资金费率、标记价格

## 九、专题二：第 5.5 周分布式一致性与消息可靠性逐日清单

> 目标：能针对"充值入账"和"提币"两个场景，讲清幂等、消息可靠、乱序、补偿、对账的完整方案。建议与第 6-7 周充值链路并行实践。

### Day 1：本地消息表与事务消息

**学习内容**
- 问题场景：充值监听器扫到区块 → 需要发 Kafka → 消费者入账。如果"写数据库"和"发 MQ"不在同一事务，一方成功一方失败怎么办？
- 本地消息表方案：业务数据 + 消息记录在同一数据库事务中提交；后台任务轮询消息表发送 MQ，成功后标记已发送
- 失败补偿：发送失败重试 + 超过阈值告警人工介入
- 与事务消息（RocketMQ 半消息）的对比：本地消息表更简单可控，不依赖 MQ 特性

**必读/参考方向**
- 结合第 6-7 周充值链路，设计 `deposit_record` 和 `outbox_message` 两张表在同一事务写入

**自测问题**
1. 本地消息表中，消息状态有哪些？从"待发送"到"已发送"之间如果进程崩溃，重启后如何恢复？
2. 消费者收到消息后处理失败，是让 MQ 重试还是记录失败表人工处理？各自的适用场景？

**交付**：画出充值场景的"本地消息表 + 轮询发送"时序图。

### Day 2：消费幂等与消息乱序

**学习内容**
- 消费幂等：每条消息携带唯一业务流水号（如 `tx_hash + log_index`），消费者用 Redis 或数据库唯一索引判重
- 乱序问题：同一用户的充值/提币事件可能乱序到达。按 user_id 或 address 分区保证同 key 有序
- 版本号/序号去重：如果消息不带全局顺序，用业务版本号拒绝旧消息
- 重复消费的后果：充值重复入账（资损）、提币重复释放冻结（资损）

**必读/参考方向**
- 已有 Redis 分布式锁基础，此处聚焦"判重键的设计"

**自测问题**
1. 链上同一笔交易可能产生多个 Event Log，判重键应该用什么？为什么不能用 tx_hash 单独判重？
2. Kafka 分区数 = 3，用户 A 的充值事件和提币事件被分到不同分区，可能乱序。如何保证同一用户的事件有序？

**交付**：设计充值消费者的幂等判重方案（表结构 + 判重逻辑伪代码）。

### Day 3：接口结果不确定与状态机幂等

**学习内容**
- 场景：提币时调用节点广播交易，超时返回。交易可能已上链也可能没上链。
- 错误做法：直接重试广播 → 可能发出两笔交易（如果 Nonce 不同）或重复提币
- 正确做法：先落库（提币请求状态 = 广播中，记录 Nonce 和 tx_hash 候选）→ 查询节点该 Nonce 的状态 → 根据链上结果更新
- 状态机幂等：提币状态只能单向流转，每个状态转换的条件明确，重复请求返回已有结果而非重新执行

**必读/参考方向**
- 结合第 8 周提币状态机设计

**自测问题**
1. 提币广播超时后，如何判断交易是否已上链？查 Nonce 还是查 tx_hash？
2. 如果用户重复提交同一笔提币请求（相同参数），系统应返回什么？如何防止生成两笔提币？

**交付**：画出提币"广播中→已上链/已失败"的状态转换图，标注每个转换的查询动作。

### Day 4：对账兜底与差错处理

**学习内容**
- 链上对账核心：链上余额/流水 vs 钱包系统记录 vs 用户账本余额，三方逐项核对
- 常见差异类型：时间差（链上已确认但系统未处理）、遗漏/重复入账、Reorg 回滚、未知代币转入
- 差异处理策略：时间差等下一轮自动匹配；系统问题修复后回填；资金异常减少立即升级
- 对账频率：T+1 全量对账 + 实时异常告警（单笔大额、余额骤降）

**必读/参考方向**
- Safeheron 加密资产对账指南：三方对账、差异分类、自动化思路

**自测问题**
1. 对账时发现链上地址余额比系统记录多 100 USDT，可能的原因有哪些？按优先级如何排查？
2. Reorg 导致已入账的充值被回滚，对账系统如何发现？应该自动回滚还是人工确认？

**交付**：设计一张对账差异表的字段（差异类型、严重级别、处理状态、关联 tx_hash），并写出 T+1 对账任务的执行步骤。

### Day 5：综合场景串联 + 自测

**学习内容**
- 把前四天的内容串成一条线：充值从扫块到入账（消息表+幂等+对账）、提币从请求到确认（状态机+查询+对账）
- 对比"简单重试"和"有状态恢复"的本质区别：前者假设操作无副作用，后者承认操作可能已生效但结果未知
- 复盘 JD 原话："正确处理接口结果不确定、服务中断及异步处理失败，而非简单依赖重试解决问题"——用自己的话解释
