## 一、为什么 CEX 后端必须先学复式记账？

先说结论：**CEX 的钱不是"一个余额字段"，而是一本账。**

大多数人第一反应会设计成这样：

```
user_balance (user_id, currency, balance)
-- 充值：UPDATE user_balance SET balance = balance + 100
-- 提币：UPDATE user_balance SET balance = balance - 100
```

这个设计在 demo 里能跑，在 CEX 里三天就出事，原因有三个：

1. **余额不可审计**。用户说"我昨天明明有 1000 USDT，怎么今天只有 900"，你只能翻业务日志猜，账本里没有任何证据链。
2. **无法对账**。链上有 16027 条充值记录，你只有一个 `balance` 字段，怎么证明"平台欠用户的钱 = 用户余额之和"？算不出来。
3. **出错无法定位**。某个 bug 多扣了 1 USDT，你不知道是哪一笔业务扣的、扣给谁了、该退给谁。

复式记账解决的正是这三件事：**每一分钱的变动都有来源（借方）、有去向（贷方）、有业务单号、有变动后余额**。这本账同时是审计证据、对账依据、故障排查的线索。

面试里问"你们账本怎么设计的"，答"我们用了复式记账，借贷必相等，分录可重建余额"和答"我们有个 balance 字段，扣减加了行锁"，是两个物种。

## 二、会计恒等式：从会计学翻译到 CEX

### 2.1 原始形式

会计学的基本恒等式：

```
资产 = 负债 + 所有者权益
```

含义：企业拥有的东西（资产），要么是借来的（负债），要么是股东自己的（所有者权益）。

举个最朴素的例子：你开一家店，自己投了 100 万（所有者权益），又找银行借了 50 万（负债），那你手里有 150 万（资产）。`150 = 50 + 100`，恒等成立。

### 2.2 翻译到 CEX：谁是谁

CEX 的特殊性在于：**用户充进来的币，在法律和会计上是平台欠用户的债**。用户把 100 USDT 充到交易所，这 100 USDT 进了平台的钱包（平台资产 +100），同时平台对用户产生了一笔"应付 100 USDT"的义务（平台负债 +100）。

所以 CEX 里的恒等式长这样：

```
平台资产（热钱包 + 冷钱包 + 归集账户里的币）
  = 平台负债（所有用户余额之和）+ 平台自有权益（手续费收入等）
```

在系统设计层面，我们更关心的是**负债侧的细分**，也就是路线里写的：

```
用户可用（available）+ 用户冻结（frozen）= 用户总额（total）
```

这三者都在"平台负债"这个大类下面。`total` 不是独立的一个数，它是 `available + frozen` 的生成列——这一点第 3 天写 DDL 时会重点强调，今天先建立直觉：**用户的总额永远是"可用 + 冻结"，冻结只是把钱从"能动"挪到"不能动"，总额不变。**

### 2.3 恒等式在系统里的三个"必须随时成立"

| 恒等式 | 含义 | 谁破坏它 = 什么事故 |
|---|---|---|
| `available + frozen = total`（每个账户） | 单账户内部自洽 | 冻结/解冻写错 → 用户总额凭空多出或消失 |
| `Σ 所有用户 total = 平台应付负债` | 用户侧汇总自洽 | 平台少记负债 → 资损，平台悄悄欠钱 |
| `Σ 所有分录的 debit = Σ 所有分录的 credit` | 账本自身平衡 | 分录不平 → 账本不可信，对账永远不平 |

第三条是整个账本系统的**最后一道防线**。前面两条是业务规则，第三条是数学规则——只要 `post()` 拦得住不平的分录，账本就不可能出现"凭空多钱/少钱"。

> **面试点**：面试官常问"你怎么保证账本不会算错"。答案不是"我代码写得好"，而是"我在 `post()` 入口强制 `sum(debit) == sum(credit)`，不平直接抛异常并告警，不落库"。这是用数学约束兜住业务 bug。

## 三、借贷必相等：最容易被误解的一条

### 3.1 常见误解："一加一减"

很多人理解复式记账就是"一个账户加、一个账户减，加起来是零"。**这个理解是错的**，错在把"借贷"当成了"加减"。

正确的表述是：**有借必有贷，借贷必相等**。一笔业务至少涉及两条 posting（分录明细），所有借方金额之和必须等于所有贷方金额之和。

关键在于：**借方和贷方不是"正负"，而是"账户性质决定方向"**。同一个方向（比如借方）在不同类型账户上，可能表示增加，也可能表示减少。

### 3.2 会计上的借贷规则（记住这张表就够用）

| 账户类型 | 借方（DEBIT） | 贷方（CREDIT） |
|---|---|---|
| 资产类 | 增加 ↑ | 减少 ↓ |
| 负债类 | 减少 ↓ | 增加 ↑ |
| 费用/损失类 | 增加 ↑ | 减少 ↓ |
| 收入/权益类 | 减少 ↓ | 增加 ↑ |

注意负债类和资产类是**反的**：资产借方增，负债借方减。这不是拍脑袋定的，而是从"资产 = 负债 + 权益"这个等式推出来的——等式左边（资产）增加时记借方，等式右边（负债/权益）增加时就必须记贷方，才能保持等式平衡。

### 3.3 在 CEX 里怎么落地

CEX 用户余额在会计上属于**平台负债**（平台欠用户的）。所以：

- 用户余额**增加** → 记**贷方（CREDIT）**
- 用户余额**减少** → 记**借方（DEBIT）**

这跟很多人的直觉相反——用户"充了 100 USDT"，直觉是"加钱"，应该记"加"，但会计上这是平台负债增加，记贷方。

**但实际工程里不必死守会计教科书的方向约定**。路线里给的表结构是 `direction(DEBIT/CREDIT)` + `account_id`，具体每个账户用借方还是贷方表示增加，取决于你在 `account` 表里怎么定义账户类型。工程上常见的简化做法是：

> **在同一个 `account` 账户内部，冻结/解冻这类"内部转移"用 `available` 和 `frozen` 两个子账本来表达；跨账户的资金流动，用一组借方 + 贷方 posting 表达，并保证该组 posting 的 debit 总和 = credit 总和。**

无论你选哪种约定，**唯一不可妥协的规则是：每组分录 debit 之和 == credit 之和**。方向约定可以在团队内统一，但平衡校验不能省。

## 四、四大场景手写分录（今天的核心练习）

下面四组必须**用纸笔手写**，不要用电脑。手写能逼你想清楚"钱从哪来、到哪去、这笔业务该不该产生分录"。每个场景我会先给业务描述，再给分录，最后给一句"为什么"。

### 场景 ①：用户充值 100 USDT

**业务描述**：用户在链上转了 100 USDT 到平台充值地址，链上确认数够了，系统入账。

**资金流向**：链上 → 平台热钱包（平台资产 +100）；用户 FUND 账户可用余额 +100（平台负债 +100）。

**分录**：

| 账户 | 方向 | 金额 | 说明 |
|---|---|---|---|
| 平台热钱包（资产类） | 借 DEBIT | 100 | 平台资产增加 |
| 用户 FUND.available（负债类） | 贷 CREDIT | 100 | 平台欠用户的债增加 |

**为什么**：资产增加记借方，负债增加记贷方，两边都是 100，平衡。

**工程提醒**：路线里有一句话非常重要——"确认数不足能不能落账？（不能，`CREDITED` 之前分录不写）"。也就是说，链上事件到了、但还没到确认数门槛时，只更新链上事件表的状态，**不写账本分录**。只有确认数够了、状态变 `CREDITED`，才调 `post()` 写这组分录。否则一旦发生 reorg，你已经入账的钱要回滚，账本就会出现"反向冲正"的脏数据。

### 场景 ②：资金账户划 100 USDT 到现货账户

**业务描述**：用户把 100 USDT 从 FUND（出入金账户）划到 SPOT（现货账户）。

**资金流向**：平台负债总额不变，只是"欠在哪个账户"变了。FUND.available 减 100，SPOT.available 加 100。

**分录**：

| 账户 | 方向 | 金额 | 说明 |
|---|---|---|---|
| 用户 FUND.available | 借 DEBIT | 100 | 该子账负债减少 |
| 用户 SPOT.available | 贷 CREDIT | 100 | 该子账负债增加 |

**为什么**：这是平台负债内部的**结构变化**，不涉及资产，所以总额不变。这组分录一借一贷各 100，账本平衡；同时 `account_transfer` 表要写一张划转单（`transfer_no / from_account_id / to_account_id / amount / status`）。

**工程提醒**：路线里反复强调"划转是账务动作，不是 `update account set available = available - 100`"。区别在于：写单据 + 写分录，事后能回答"这 100 是谁、什么时候、从哪划到哪"；直接 UPDATE 字段，事后什么都查不到。**划转单本身就是幂等键**——同一 `transfer_no` 重复提交，靠唯一键挡住。

### 场景 ③：下买单冻结 50 USDT

**业务描述**：用户在 SPOT 账户下了一个限价买单，需要冻结 50 USDT。

**资金流向**：SPOT.available 减 50，SPOT.frozen 加 50。总额不变。

**分录**：

| 账户 | 方向 | 金额 | 说明 |
|---|---|---|---|
| 用户 SPOT.available | 借 DEBIT | 50 | 可用减少 |
| 用户 SPOT.frozen | 贷 CREDIT | 50 | 冻结增加 |

**为什么**：这是"同一账户类型内部"的可用/冻结转移。**关键点：`total` 不变**。用户的钱还在他名下，只是暂时不能动。这就是为什么 `total` 必须是 `available + frozen` 的生成列——它是恒等式的物化，冻结动作不应该、也不能改变它。

**工程提醒**：冻结和下单必须同事务（路线 W8 Day 5-6 会讲）。冻结成功但落单失败，会留下"孤儿冻结"，用户钱被冻着但没有订单，只能靠对账捞出来人工解冻。这种事故很典型。

### 场景 ④：成交后扣 1 USDT 手续费

**业务描述**：一笔成交完成，平台收取 1 USDT 手续费。

**资金流向**：用户 SPOT.available 减 1（用户侧负债减少）；平台手续费收入账户加 1（平台权益增加）。

**分录**：

| 账户 | 方向 | 金额 | 说明 |
|---|---|---|---|
| 用户 SPOT.available | 借 DEBIT | 1 | 用户可用减少 |
| 平台手续费收入（收入/权益类） | 贷 CREDIT | 1 | 平台收入增加 |

**为什么**：手续费是**平台内部权益转移**——用户的钱变成平台的收入，**不发生任何链上交易**。所以它和链上 gas 必须分开记（路线 W7 Day 1-2 强调"手续费是平台内部权益转移，不发生链上交易；gas 是真实支出且随拥堵浮动"）。混在一起，毛利永远算不清。

**工程提醒**：路线 W2 Day 5-6 给的四场景是"充值落账 / 下单冻结 / 成交清算 / 提币失败解冻"，今天这四组是它的简化版，目的是先建立方向感。成交清算的完整版（Taker 冻结扣减、Maker 可用增加、手续费单独一组）在 W2 再细化，今天写到"手续费单独成组"这个粒度就够。

## 五、三大账户隔离：为什么 FUND / SPOT / PERP 必须分开

### 5.1 三个账户各自的职责

| 账户类型 | 职责 | 典型操作 |
|---|---|---|
| `FUND` | 出入金专用 | 链上充值入账、提币扣减、与 SPOT/PERP 划转 |
| `SPOT` | 现货交易 | 下单冻结、成交清算、手续费扣除 |
| `PERP` | 合约交易 | 保证金占用、盈亏结算、资金费率 |

### 5.2 为什么合约账户不能和现货共用一张余额表

路线里给的理由很直接：**"保证金率计算会把现货余额算进可用保证金，风控直接算错"**。展开说：

合约的保证金率公式里，"可用保证金"是一个关键输入。如果现货和合约共用一张余额表，那么用户 SPOT 账户里的 1000 USDT 会被保证金率计算当成"可以拿来扛合约亏损的钱"，用户的合约仓位就会显得很安全，系统不会触发强平。但事实上这 1000 USDT 可能是用户准备买现货的，不是来扛合约的——一旦行情反向，平台要么不公平地强平（把现货钱也算进去），要么该强平时不强平（平台兜底亏损）。**两种都是事故。**

隔离账户后，合约风控只看 `PERP` 账户的余额，现货的钱不参与保证金计算，边界清晰。

### 5.3 为什么 `perp_position` 必须独立成表

路线原话：**"持仓有方向、杠杆、开仓价、保证金模式，塞进余额表就变成'余额带方向'，所有聚合查询全废"**。

具体展开：持仓需要记录 `side`（多/空）、`leverage`（杠杆倍数）、`entry_price`（开仓均价）、`margin_mode`（逐仓/全仓）、`margin`（占用保证金）。这些字段和"余额"（available/frozen/total）是**两个维度**的东西。硬塞进一张表，你会得到：

- `account` 表里一半行是"余额"语义、一半行是"持仓"语义，任何"按 user 聚合余额"的查询都要先过滤掉持仓行；
- `available + frozen = total` 这个约束对持仓行不成立，生成列和 CHECK 约束直接失效；
- 一个用户可能同时持有多个 symbol 的多个方向仓位，而余额表的主键 `(user_id, account_type, currency)` 根本装不下。

所以持仓独立成 `perp_position` 表，唯一键 `uk_user_symbol_side_mode (user_id, symbol, side, margin_mode)`，和余额表通过 `user_id` 关联但互不侵入。

## 六、账户流转图 v1（今天的产出物之一）

用纸笔画，不要用画图软件。要求：三个方框（FUND / SPOT / PERP），双向箭头，箭头上标注"划转单 `transfer_no`"，外面画一个"链上充值地址"指向 FUND，一个"提币出口"从 FUND 出去。

示意结构（你纸上应该更完整）：

```
        链上充值事件
              │  (确认数达标才入账)
              ▼
        ┌──────────┐   划转单 transfer_no   ┌──────────┐
        │   FUND   │ ◄──────────────────► │   SPOT   │
        │ available│                       │ available│
        │ frozen   │                       │ frozen   │
        └──────────┘                       └──────────┘
              │ 划转单                          │
              ▼                                 │ 下单冻结/成交清算
        ┌──────────┐ ◄──────────────────────────┘
        │   PERP   │  划转单
        │ available│
        │ frozen   │
        └──────────┘
              │
              ▼
        提币出口（扣 fee + gas_cost）
```
