# 入口限流方案设计（第 2 周交付 3 · 四道闸 + 有界排队）

> 适用场景：链上读接口（尤其 `eth_getLogs` 类高配额消耗查询）封装成对外 API 后，回答“调用太快/太多怎么办”。
> 定位是为后续资产网关“对外 API 安全”“节点 RPC 调用保护”打底；**默认关闭**（`security.rate-limit.enabled=false`），
> 关闭时拦截器完全不挂到 MVC 链，对现有本地开发链路零影响。
> 与 RPC 侧漏桶（Resilience4j `ratelimiter`，见 README 5.2）的分工：漏桶垫在监听器与节点之间做**下游平滑**，
> 本方案守在**对外入口**做突发放行与洪峰防护。

---

## 1. 需求拆解：两个正交的维度

“限流”其实是两类不同诉求，混在一起会导致要么防不住洪峰、要么误伤正常用户：

| 维度 | 控制的是 | 典型诉求 | 机制 |
|---|---|---|---|
| **速率限流** | 每秒**到达**多少请求 | 每用户 5 秒最多 N 次；全局每秒最多 M 次 | 令牌桶（限速） |
| **总量配额** | 累计**消耗**多少 | 每用户每天最多 Q 次 | 计数器 `INCR + EXPIRE` |
| **并发限流** | 同一时刻**正在处理**多少 | 处理慢时防在飞请求堆垮 DB/线程 | 信号量（限并发） |

“1 万用户 1 秒内同时访问”本质是**瞬时高 QPS 洪峰**，主要靠全局限速解决；但光限速不够，需配**并发上限**兜底慢请求堆积。
因此本方案把三者组合成一条**四道闸**串联判定链。

## 2. 四道闸架构（`RateLimitInterceptor` 编排，判定委托 `RateLimitGuard`）

请求需**依次通过全部闸门**才放行，任一挡住即返回 429：

```
① 全局速率  →  ② 每用户速率  →  ③ 每用户日总量配额  →  ④ 并发槽位
  (令牌桶)       (令牌桶/分key)     (日计数器)          (信号量/有界排队)
```

- **顺序刻意**：前三道是纯检查、不占资源；最后一道才占用处理槽位并要求归还。
  避免“请求一边占着槽位一边等速率令牌”白白锁死并发预算。
- **闸门可独立关**：速率类参数设 `0` 或负、每用户/配额开关置 `false`，即跳过对应闸门（如只用并发闸门兜底）。
- 判定结果统一封装为 `RateLimitDecision`：放行携带并发槽位**归还凭据** `release`；拒绝带 `rejectReason` 与 `retryAfterMs`（用于 429 的 `Retry-After` 头）。

## 3. 两种模式：LOCAL vs DISTRIBUTED（`security.rate-limit.mode`）

多实例部署是本方案的核心约束——单机内存桶在多副本下各限各的，总吞吐 = 单机速率 × 副本数，口径不统一。

| | LOCAL（默认） | DISTRIBUTED |
|---|---|---|
| 全局速率 | Guava `RateLimiter`（单实例口径） | Redisson `RRateLimiter` `RateType.OVERALL`（全集群合计口径） |
| 每用户速率 | Guava Cache 惰性建桶 + `expireAfterAccess` 回收 | Redis 固定窗口计数器（Lua 原子 INCR/首次设 TTL，key 自带 TTL 自净） |
| 每用户日配额 | Guava Cache 存 `AtomicInteger` | Redis 计数器按天分键 |
| 并发槽位 | JDK 公平 `Semaphore` | Redisson `RPermitExpirableSemaphore`（带租期） |
| 外部依赖 | 无（进程内存） | 需 Redis 就绪 |
| 适用 | 单实例 / 本地联调 | **多实例部署统一口径** |

> 守卫接口 `RateLimitGuard` 屏蔽两套原语差异，`SecurityConfig` 按 `mode` 选装对应实现；被拒请求一律**不消耗配额**（LOCAL 回退计数、DISTRIBUTED Lua 内回退，两侧同口径）。

## 4. 两种洪峰策略：FAST_FAIL vs BOUNDED_QUEUE（`security.rate-limit.queue-policy`）

| 策略 | 行为 | 适用 |
|---|---|---|
| **FAST_FAIL**（默认） | 抢不到令牌/许可**立即 429**，不占线程等待（配 `timeout-ms=0`） | 洪峰快速打回，保护自身不被拖垮 |
| **BOUNDED_QUEUE** | 最多 `queue-capacity` 个请求排队，每队最长 `timeout-ms`，超预算才 429 | 平滑吸收短时突发，牺牲少量延迟 |

### 4.1 有界排队原语（`BoundedQueueRateLimiter`）

**语义**：最多 `maxConcurrent` 个请求同时在处理；另有最多 `queueCapacity` 个请求排队等待；每个等待者最多阻塞 `timeoutMs`。
三者之外的请求**立即拒绝**——排队是“有界的”，不会因洪峰无限堆积拖垮调用方线程与内存。

**实现取舍**：不用 `Semaphore(maxConcurrent + queueCapacity)` 一把梭——那样无法区分“正在处理”与“正在排队”，也无法对“排队人数”单独设上限。
本原语用 **公平信号量**（保证 FIFO 排队顺序）+ **等待计数器**（`AtomicInteger`，超 `queueCapacity` 立即拒）双约束，语义精确。

**与令牌桶互补**：令牌桶管“到达速率”（每秒最多几个），本原语管“在飞数量 + 排队预算”。洪峰下两者共同决定分层行为：放行 → 排队 → 超预算 429。

## 5. 为何入口用令牌桶而非漏桶

运营后台批量补拉历史日志是**合法突发**：令牌桶允许把闲置时段积累的令牌瞬间消耗，漏桶则严格匀速、不放大突发会把正常批量请求拖慢。
速率上限按 Infura 日配额反推（`日配额 / (86400 × 单次请求平均 RPC 次数)` 取安全下限）。
漏桶在此仍作为下游 RPC 平滑手段保留（Resilience4j 侧），并与令牌桶做行为对比实验（见 `RateLimiterComparisonTest`、`LeakyBucketRateLimiter`）。

## 6. 每用户维度的身份 key（`ClientIdentityResolver`）

闸门②③按调用方分 key，优先级：

1. **JWT `sub`**：`JwtAuthInterceptor` 验签通过后把 `claims` 写入请求属性 `web3.jwt.claims`，解析出 `sub:xxx`；
2. 无 JWT 时回退 `X-Forwarded-For` 首跳 → 容器对端地址（`ip:xxx`）；
3. 均解析不到 → `anonymous` 兜底（返回非 null，保证限流维度不丢）。

> 因此 JWT 与限流存在**装配顺序依赖**：`SecurityConfig` 注册拦截器时 JWT 先于限流，限流才能拿到 `sub`。
> 未开 JWT 时限流自然按 IP 分桶，仍可用。

## 7. 并发槽位的生命周期与泄漏防护

- **占用**在 `preHandle`，**归还**在 `afterCompletion`——不能用 `postHandle`：它在异常路径不执行会泄漏槽位；`afterCompletion` 对 `preHandle` 返回 true 的请求必定执行。
- **DISTRIBUTED** 下许可带 `concurrency-lease-ms` 租期：实例崩溃未能归还时到期自动释放，防许可泄漏；正常路径 `afterCompletion` 主动 release，幂等由 permitId 保证。
- 归还动作内部兜底（分布式靠租期自愈），拦截器再挡一层运行时异常，保证响应收尾不受影响。

## 8. 配置项一览（`security.rate-limit.*`）

| 配置 | 环境变量 | 默认 | 说明 |
|---|---|---|---|
| `enabled` | `API_RATE_LIMIT_ENABLED` | false | 总开关；关闭时拦截器不注册 |
| `mode` | `API_RATE_LIMIT_MODE` | LOCAL | LOCAL / DISTRIBUTED |
| `queue-policy` | `API_RATE_LIMIT_QUEUE_POLICY` | FAST_FAIL | FAST_FAIL / BOUNDED_QUEUE |
| `permits-per-second` | `API_RATE_LIMIT_QPS` | 5 | ① 全局速率（DISTRIBUTED 为全集群口径）；0/负=关 |
| `timeout-ms` | `API_RATE_LIMIT_TIMEOUT_MS` | 0 | 等令牌/许可超时；BOUNDED_QUEUE 下必填且 >0 |
| `max-concurrent` | `API_RATE_LIMIT_MAX_CONCURRENT` | 20 | ④ 并发槽位上限，与下游容量对齐；0/负=关 |
| `queue-capacity` | `API_RATE_LIMIT_QUEUE_CAPACITY` | 50 | 排队区容量（BOUNDED_QUEUE 生效） |
| `concurrency-lease-ms` | `API_RATE_LIMIT_CONCURRENCY_LEASE_MS` | 60000 | 并发许可租期（仅 DISTRIBUTED） |
| `per-user-enabled` | `API_RATE_LIMIT_PER_USER_ENABLED` | false | ② 每用户速率闸门开关 |
| `user-permits-per-second` | `API_RATE_LIMIT_USER_QPS` | 2 | 每用户速率 |
| `quota-enabled` | `API_RATE_LIMIT_QUOTA_ENABLED` | false | ③ 每用户日总量配额闸门开关 |
| `user-daily-quota` | `API_RATE_LIMIT_USER_DAILY_QUOTA` | 1000 | 每用户每日上限（次/天） |

## 9. 交付验证

- **离线单测**（不依赖真实 Redis/DB）：
  - `LocalRateLimitGuardTest`：隔离验证四道闸各自行为（全局速率 / 每用户速率分桶 / 日配额用尽不回退消耗 / 并发快速失败与归还复用）；
  - `BoundedQueueRateLimiterTest`：有槽即占、排队区满立即拒、有界等待超时拒、归还后槽位复用、非法参数快速失败；
  - `ClientIdentityResolverTest`：sub → X-Forwarded-For → 对端地址 → anonymous 优先级；
  - `RateLimiterComparisonTest`：令牌桶放突发 vs 漏桶匀速的行为对比。
- **DISTRIBUTED 口径**需在 Redis 就绪、`mode=DISTRIBUTED` 下实跑验证：多副本合计不超全局速率、许可租期到期自愈。
