# web3-backend 技术选型文档

> 面向 Web3j 以太坊后端应用（钱包/充值提币/链上数据查询场景）的完整技术选型与落地说明。
> 本文档与项目当前骨架代码一一对应，基线为 **JDK 21 + Spring Boot 4.1.2 + Web3j 6.1.0**（已于本机实机验证）。
> 链上数据写入链路（分页拉取 → 解码 → 事件与游标同事务落库）已完成主网 USDT 区间的实机对账验收。

```
│              SyncCursorService / TransferEventStoreService  │
├───────────┬──────────────────┬───────────────────────────┤
│ web3j     │ wsWeb3j          │ Scanner（Scheduler/XXL-Job  │
│ (HTTP RPC │ (WebSocket 长连接 │  + Redisson 锁)            │
│  OkHttp)  │  newHeads/logs)  │  区块轮询 → 进度落库         │
├───────────┴──────────────────┴───────────────────────────┤
│  持久层  MyBatis-Plus → MySQL（游标与事件同事务）           │
│  缓存/锁 → Redis（游标缓存 + Redisson 锁）                  │
├──────────────────────────────────────────────────────────┤
│  可观测  Actuator + Prometheus     文档  Swagger UI         │
└──────────────────────────────────────────────────────────┘
```

双 `Web3j` 实例是刻意设计：HTTP 侧承载可幂等重试的请求-响应型调用，WebSocket 侧只承载长连接推送订阅，
两者的连接生命周期、线程模型与容错策略完全不同，混用一个实例会让熔断/重试语义污染订阅链路。

## 四、关键设计说明

### 4.1 链上交互（Web3j + Infura）
- `Web3jConfig` 基于 `HttpService(infura.http-url)` 构建单例 `Web3j`，`destroyMethod = "shutdown"` 释放 OkHttp 连接池；连接惰性建立，缺 `projectId` 也不阻塞启动。
- Infura Project ID 通过环境变量 `INFURA_PROJECT_ID` 注入，**不写入代码库**。
- 默认对接 **主网**（`chainId=1`）；切 Sepolia 或本地 Anvil 改 `web3.infura.http-url` / `web3.websocket.url` 与 `chain-id`（配置文件中保留注释行）。
- WS 端点由 `web3.websocket.url` 单独提供，`web3.infura.ws-url` 已废弃（配置中删除，字段暂无消费方）。
- 事件订阅使用 `newHeadsNotifications()` / `logsNotifications(addresses, topics)`（`eth_subscribe` 服务端推送）。
  **注意 `ethLogFlowable(filter)` 不是推送**：它内部是 `eth_newFilter` + 每 15s 轮询 `eth_getFilterChanges`，与 WebSocket 无关，实时性差的根因通常在这。

### 4.2 RPC 容错（Resilience4j）
- 查询方法标 `@Retry(name = "rpc")` + `@CircuitBreaker(name = "rpc")`；分页拉日志的单段调用标 `rpc-segment`，
  使重试粒度落在单段上，避免"一段失败重跑整区间"。
- `rpc`：最多 3 次（间隔 500ms）；`rpc-segment`：最多 5 次 + 指数退避（×2）+ 随机抖动（因子 0.5），
  因为分页拉取撞的常见不是硬故障而是 429 限流，固定 500ms 密集重击只会让限流更严重。
- `rpc-segment` 额外挂 `@RateLimiter`（5 次/秒、等待上限 5s）主动平滑吞吐，而不是等节点返 429 再退。
- 熔断策略：滑动窗口 20、最小调用数 5、失败率 ≥50% 熔断 30s、半开 5 次。
- 兜底由 `GlobalExceptionHandler` 统一转响应码：RPC/节点错误（`IllegalStateException`）→ `502`，交易异常 → `500`，参数非法 → `400`。
- Boot 4 下必须引 `spring-boot-starter-aspectj`（`spring-boot-starter-aop` 已被移除），否则注解不生效。

### 4.3 区块扫描（Scheduler + XXL-Job + Redisson）
- `BlockScanner.doScan`：取最新高度 → `LambdaQueryWrapper` 查 `block_sync_state` → `insert` 或 `updateById`。
- **双通道**：`@Scheduled(fixedDelayString = "${web3.scanner.interval-ms:30000}")` 与 `@XxlJob("blockScanHandler")`；
  当前源码里 `@Scheduled` 处于注释状态，实际只有 XXL-Job 通道（需 `xxl.job.enabled=true` 并接入调度中心）。
- **Redisson `tryLock`** 保证多实例仅一个节点执行，未抢到锁跳过本轮；解锁前判 `isHeldByCurrentThread()`。

### 4.4 WebSocket 实时订阅与资源释放
- 订阅在 `ApplicationReadyEvent` 后启动，`subscribe-new-heads` 控制 newHeads 开关；订阅句柄统一放 `CompositeDisposable`。
- `includeRawValues=true`（`new WebSocketService(client, true)`）时事件字段为原始 hex，需 `Numeric.toBigInt` 自行解码；
  `websocket.events.Log` 与 `core.methods.response.Log` 的取值类型不同，不能直接复用解析代码。
- `logsNotifications` 内部对入参直接调 `isEmpty()`，传 `null` 会 NPE → 合约列表为空时传空集合。
- 释放顺序：`@PreDestroy` 先 `dispose()`（发 `eth_unsubscribe`）→ `webSocketService.close()`；`wsWeb3j.shutdown()` 交给 Bean `destroyMethod` 最后执行。
- 语义边界：`eth_subscribe("logs")` 无区块区间概念、不回报重组，只做"提前发现"，落库以区间重扫为准。

### 4.5 代理穿透（本项目特有约束）
| 通道 | 底层实现 | 是否认 JVM 代理参数 | 方案 |
|---|---|---|---|
| HTTP RPC | OkHttp | 需显式设置 | `Web3jConfig` 构造带 `Proxy(HTTP)` 的 `OkHttpClient` |
| wss | Java-WebSocket（`org.java_websocket`） | **完全不认**（`Proxy.NO_PROXY`，`setProxy(HTTP)` 也不发 CONNECT） | `util/ProxyTunnel` 手工 `CONNECT host:443` → `SSLSocketFactory.createSocket(plain,...)` 升级 TLS → `WebSocketClient#setSocket(ssl)` |

隧道实现的两个坑：读代理响应必须逐字节到 `\r\n\r\n`（带缓冲的流会吞掉 TLS 字节）；
不能对 socket 的流做 try-with-resources（关流会连带关掉隧道 socket）。`setSocket` 虽标废弃，
但 `setSocketFactory` 分支会对目标地址重新 connect 从而绕过隧道，只有预置已连 socket 这条路可用。

### 4.6 eth_getLogs 分页与节点限制
- 按 `web3.infura.log-chunk-size` 分段循环，段内交给 `rpc-segment` 做网络级重试；`toBlock` 超链高自动截断（整区间接口），单页接口 `fetchTransferLogPage` 不截断（链高截断由补拉编排层完成，避免页边界被偷改后游标推过头）。
- **Transfer 精确过滤**：`buildFilter` 用 `addSingleTopic(TransferEventDecoder.transferEventTopic())`，
  只拉 `topic[0] = keccak("Transfer(address,address,uint256)")` 的日志。该 topic 由 `EventEncoder.encode(EventConsts.TRANSFER_EVENT)` 算出，
  监听器与补拉共用同一个方法，避免两处过滤条件漂移；写入前再按 topic 蓝图解码一次，非 Transfer 日志丢弃。
- **自适应缩小跨度（已启用）**：单段命中上限时正则解析错误里的建议区间并优先采纳（节点已按结果密度算好），
  建议不合理（不小于本段）则退化为二分；保留 **`MIN_CHUNK_SPAN = 16` 块护栏**，缩到护栏仍被拒则直接抛出，避免无限递归。
  只对上限类错误生效（`returned more than N results` / `block range too wide` / `too many events`），
  `header not found` 这类错误缩跨度无意义，直接抛出走重试/熔断。
- 正确性前提：子段结果按区块升序合并等于本段完整结果，因此“本段全部拉完”可验证，调用方才能把游标推到段末。

### 4.7 历史补拉：游标与落库的一致性取舍
监听器重启/故障后要把停机期间的链上状态补齐，核心问题是“**不漏单也不重复**”。选型结论：

| 取舍点 | 结论 | 理由 |
|---|---|---|
| 游标存在哪 | MySQL `block_sync_state.latest_scanned_block` 为事实来源，Redis 只做读加速 | 游标必须与事件同事务提交，Redis 无法参与 MySQL 事务；若以 Redis 为事实，一次过期/重启就会丢进度 |
| 游标怎么推 | `upsertCursor` 用 `ON DUPLICATE KEY UPDATE latest_scanned_block = GREATEST(…) ` | 多实例并发或人工重跑时保证游标**单调前移**，不会把已处理区间“回档”造成重复入库以外的语义混乱 |
| 事件怎么写 | `INSERT IGNORE` + 唯一键 `(chain_id, transaction_hash, log_index)`，每 500 行一批 | 重放安全（幂等）靠数据库约束而非分布式事务；分批控制单语句包大小，避免 `max_allowed_packet` 拒接 |
| 事务边界 | 一页一个事务：事件写入与游标推进同提交（`rollbackFor = Exception.class`） | 拆开会出现“游标前移但事件没入库”的丢单；一页为单元时崩溃最多回退一页，重拉代价可控 |
| 空页 | 不发 SQL，但照例推进游标 | 否则补齐会卡几天都没有 Transfer 的区间，循环永不前进 |
| 金额列类型 | `VARCHAR(78)` / `VARCHAR(80)` 存十进制字符串，不用 `DECIMAL` | MySQL `DECIMAL` 最大精度 65 位，容不下 `uint256`（78 位）；监听任意合约时一个异常金额就会整页回滚、游标永久卡住，而字符串写入不会失败 |
| 并发控制 | Redisson `tryLock`（同一 `chainId+contract` 互斥，不排队） | 两个任务跑同一大区间只会白白消耗 RPC 配额，失败比等待更有信息量 |
| 单次时长 | `max-blocks-per-run` 限幅 + 返回 `limited=true` | 避免单个 HTTP 请求长时间占线程；下次用同一 `fromBlock` 重调从游标自然接着跑 |

**验收数据（主网 USDT，Infura 实跑）**：`18000000→18001000` 单段 1000 块共 16027 条 Transfer，超出 Infura 单次 10000 上限，
自适应按建议区间切成 587 + 413 两段拉全；事件数与 `SELECT COUNT(*)` 一一对齐，回退游标重跑同区间 `savedCount=0`、行数不变、重复组数 0；
续拉 `18001001→18001050` 得 783 条，与独立 `eth_getLogs` 直查结果一致；`block_sync_state` 与 `web3:sync:cursor:1:0xdac1…` 两处游标相等。

### 4.8 Spring Boot 4 升级要点（已实机验证）
- **版本上界**：`spring-boot-starter-parent` 4.x 线最高 GA 为 **4.1.2**（4.2.0 仅有 M/RC，未 GA），Boot 4 基线 Java 17，JDK 21 可直接使用。
- **与 web3j 6 的耦合**：web3j 6 引入 Jackson 3（`tools.jackson`），Jackson 3 databind 依赖 `com.fasterxml.jackson.core:jackson-annotations` 中的 `JsonSerializeAs`（2.18~2.19 被移除、2.21 才恢复）。Boot 3.5.x 的 BOM 把 annotations 压到 2.19.2，会在 Bean 创建阶段抛 `NoClassDefFoundError`；Boot 4.1.2 的 BOM 给 2.21，问题消解——**Boot 与 web3j 必须同升，不是两个独立动作**。
- **starter 坐标变化**：`spring-boot-starter-aop` → `spring-boot-starter-aspectj`；MyBatis-Plus、Resilience4j 需换 `-spring-boot4` 系列。
- **Jackson 3 API 差异**：`ObjectMapper` 不可变，统一走 `JsonMapper.builder()`；`WRITE_DATES_AS_TIMESTAMPS` 从 `SerializationFeature` 移到 `DateTimeFeature`；java.time 支持内置于 databind，不再需要 `JavaTimeModule`；`PropertyAccessor`/`JsonAutoDetect` 仍来自共享的 `jackson-annotations`。
- **Spring Data Redis 4**：`GenericJackson2JsonRedisSerializer` 标 `@Deprecated(forRemoval = true)`，改用 `GenericJacksonJsonRedisSerializer`；单参 `(ObjectMapper)` 构造与旧版一致，不启用 default typing（不写 `@class`）。
- **验证结论**（本机实机）：`mvn clean compile` BUILD SUCCESS 且无 forRemoval 警告；启动 `Spring Boot v4.1.2 / Spring v7.0.10 / Tomcat 11.0.27`；
  wss 经 CONNECT 隧道成功推送 `[newHeads]` / `[logs]`；`/api/chain/status`、`/block-number`、`/logs/transfer/{contract}`、`/actuator/health`、`/v3/api-docs` 全部可用；
  临时打开 `@Scheduled` 后 `SELECT` + `UPDATE block_sync_state` 实际执行成功（`Updates: 1`）。
- **依赖树现状**：Netty 统一 4.2.19（Redisson/Vert.x 收敛），OkHttp 5.5.0，Jackson 3.1.7 与 2.21.7 双栈共存。web3j 6 会额外带入 Vert.x 5 与 AWS KMS runtime（`scope=runtime`），fat jar 体积明显上涨，按需 exclusion。

### 4.9 安全与密钥管理
- 私钥严禁硬编码：本地开发用环境变量/`.env`（勿提交），生产建议 HashiCorp Vault 或托管钱包服务（Fireblocks/Turnkey）。
- 钱包文件（keystore）已在 `.gitignore` 中排除（`wallet/`、`*.keystore`）。

### 4.10 监控
- `/actuator/health` 探活；`/actuator/prometheus` 暴露 JVM、HTTP、Resilience4j 熔断器状态指标。
- 建议告警项：RPC 失败率、区块扫描滞后高度（`block_sync_state` 与链上最新块差值）、WS 订阅是否长时间无推送、
  补拉游标是否长时间未前推（`updated_at` 落后说明任务停滞或区间卡在护栏之外）。
