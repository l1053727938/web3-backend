# 实时充值业务流程说明

> 本文只描述业务，不涉及任何技术实现。

## 1. 业务目标

7×24 小时不间断地关注链上资金动态：**只要有用户向平台收款地址转账，第一时间发现、登记为待确认充值，并通知账务部门入账**，让用户尽早就看到充值到账。

## 2. 关注范围

- 平台指定的代币转账事件（币币转账的"到账"动作）；
- 重点盯防的对象：平台热钱包地址、用户专属充值地址（即"平台收款地址清单"）；
- 地址清单由运营维护，可随时增删，增删后即刻生效，无需人工干预流程。

## 3. 正常业务流程

```
链上发生一笔转账
        │
        ▼
① 系统实时察觉到这笔转账
        │
        ▼
② 判断收款方是不是平台自己的地址
   ├─ 不是 → 与本业务无关，直接忽略
   └─ 是   → 继续
        │
        ▼
③ 核对币种：转账的代币与该地址登记的币种一致才受理
   （防止 A 币记到 B 币头上造成串账）
        │
        ▼
④ 登记一笔"待确认"充值记录
   内容包含：充值单号、付款人地址、收款地址、金额、
   所属钱包类型、关联用户、凭证信息等
        │
        ▼
⑤ 通知下游账务系统
   "有一笔新充值待处理：单号 XX，金额 XX，处于待确认状态"
        │
        ▼
⑥ 账务侧按确认规则推进后续处理
   （确认充分后正式入账、记账；本系统只负责发现和登记）
```

## 4. 业务规则

### 4.1 只认"到账平台地址"的钱
转账的收款方必须在平台收款地址清单内，且币种匹配，否则不算充值，不登记、不打扰账务。

### 4.2 先登记，后通知
一定先把充值记录正式登记在册，再知会账务。避免出现"账务收到了通知、账上却查无此单"的悬空消息。

### 4.3 同一笔转账只认一次
以链上转账凭证作为唯一识别依据：同一笔转账不论被渠道重复上报、还是事后核对时再次扫到，都只登记一次、只通知账务一次，杜绝重复入账。

### 4.4 凭证相同但内容对不上，人工裁决
如果同一凭证两次上报的金额或收款地址不一致，属于异常情况，系统不自动覆盖，挂起并告警，等人工核实后处理。

### 4.5 通知未送达可补发
登记成功但通知账务未成功时，充值记录本身不受影响；系统会标记该通知"待补发"，由补偿机制再次知会，直至送达。

## 5. 异常情况的业务口径

| 场景 | 业务处理 |
|---|---|
| 观察链路的信号中断 | 系统自动重新接上，恢复后继续关注，无需人工介入 |
| 链路"看似正常"但长时间收不到任何动态，而链上其实一直在前进 | 系统按固定时间间隔自检：拿网络另一条独立通道核对链上最新进展，确认"链在前进、自己却没收到"后，主动重建观察链路恢复接收（约一分半内发现，可调），无需人工介入 |
| 整条链长时间没有任何新动态（链本身空闲） | 自检能分辨"链没动"和"自己没收到"，链空闲时不会误判故障、不会瞎重建 |
| 短时转账过于集中，观察链路处理不过来 | 允许暂时漏看，事后由**定时自动核对**统一补齐，钱不会漏记 |
| 链上发生回退（转账被撤销） | 撤销的转账不作为充值登记 |
| 单笔登记或通知环节出错 | 不影响其他笔的处理，主流程持续运行 |

## 6. 兜底机制

除实时关注外，系统另有**定时批量核对**流程（已启用）：每隔固定时间（默认 30 秒，可调），自动把每个关注代币从**上次核对到的位置**继续往后核对，直到追平链上最新进展；核对结果同样会触发充值登记与账务通知，且同一笔转账重复核对到时不会重复入账、不会重复通知。另有人工触发的指定区间核对，用于历史补录与事后复查，两者口径完全一致。

两条纪律：
- **多节点不重复干**：同一时刻只有一台机器执行核对，其余自动让位，不会重复消耗资源或产生重复账；
- **新关注代币的历史起点由人工定**：某代币尚未建立核对进度时，定时核对默认不擅自把它从开天辟地扫一遍（工作量可能是天文数字），而是等人工首次指定区间核对、建立进度后自动接管；也可预先指定起点让定时核对直接接管。

因此实时链路的定位是“**尽早发现**”，而“**一笔不漏**”由定时自动核对保证。两者配合，既快又全。

## 7. 对外交付结果

- 财务/运营：可在充值记录中查询每一笔待确认及后续状态的充值；
- 账务系统：实时收到新充值通知，据此推进确认与入账；
- 用户：充值被快速发现，到账体验更好。
