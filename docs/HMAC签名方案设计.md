# HMAC 签名方案设计（第 2 周交付 2 · 设计文档，不含代码实现）

> 适用场景：外部合作方调用查询 API、接收第三方 Webhook 回调时验证来源与内容完整性。
> 本周只要求设计到位；代码实现排期在第 8 周提币接口安全部分。
> 与 JWT 的分工：JWT 解决“谁在调用”（身份声明），HMAC 签名解决“这条请求是否被篡改/重放”（内容完整性 + 一次性）。

---

## 1. 请求头字段约定

| Header | 说明 | 示例 |
|---|---|---|
| `X-Signature-AppKey` | 调用方标识，服务端据此查共享 secret | `partner-alice` |
| `X-Signature-Timestamp` | 请求发起时刻，毫秒时间戳 | `1762041600000` |
| `X-Signature-Nonce` | 一次性随机串（UUID），防重放核心 | `5f0c1a2e-...` |
| `X-Signature` | 下方签名串算出的 HMAC-SHA256（hex 小写） | `a3f5...` |

每个 AppKey 对应一个服务端保管的对称 secret；secret 绝不出现在请求里。

## 2. 签名串构造规则

按固定顺序拼接（`\n` 为分隔符），对拼接串计算 HMAC-SHA256：

```
HTTP Method + "\n" + Request Path + "\n" + Timestamp + "\n" + Nonce + "\n" + SHA256(Request Body)
```

- `Request Path` 不含 query string；query 参数若有防篡改需求，按 key 字典序拼进 Path 之后（v2 预留）。
- GET 请求 Body 为空字符串，`SHA256("")` 仍是固定值参与拼接。
- Body 先取 SHA-256 摘要再拼接，避免大报文进签名串，也避免边界歧义（拼接项含换行时的注入风险由摘要消除）。

任何对方法、路径、时间戳、Nonce、请求体的篡改都会导致签名不匹配，四项均不可省。

## 3. 服务端校验流程

1. 按 `AppKey` 查 secret，查不到 → 401。
2. **时间窗校验**：`|serverTime - Timestamp| <= 300000`（5 分钟），超出 → 401（同时抵御时钟异常与历史报文重放）。
3. **Nonce 防重放**：`SET sign:nonce:{appKey}:{nonce} 1 NX EX 600`（TTL = 时间窗 2 倍，覆盖窗口内全部重放可能）。
   SET 失败（key 已存在）→ 判定重放，401。原子 SETNX 同时完成“查重 + 占位”，无并发漏洞。
4. **验签**：按第 2 节规则用请求实际内容重算签名，与 `X-Signature` 做**常量时间比较**（`MessageDigest.isEqual`，防时序侧信道），不一致 → 401。
5. 全部通过 → 进入业务处理（后续再叠加 JWT scope 授权判定）。

> 顺序刻意是先廉价校验（时间窗）后昂贵校验（Redis / HMAC），且 Nonce 占位放在验签**之前**会被拒（验签失败的请求不应消耗 nonce 空间）——正确做法：验签通过后再 SETNX 占位，防止攻击者用伪造 nonce 提前投毒挤占合法请求。两步之间用“验签成功”做前置门槛。

## 4. 防重放强度说明

- 时间窗 5 分钟 + nonce TTL 10 分钟：同一请求在窗口内第二次到达必被 nonce 拦截；窗口外到达被时间戳拦截。
- 时间窗的存在意味着重放窗口是有限的（≤5 分钟），nonce 只需在窗口内存活，Redis 内存压力可控。
- 服务端幂等仍需业务层兜底（第 5.5 周“接口结果不确定”专题：请求唯一流水号 + 状态机幂等），签名层的 nonce 防不住“调用方自己重试同一业务意图”的合法重复。

## 5. 与 JWT 的适用场景对比

| | JWT | HMAC 签名 |
|---|---|---|
| 防篡改 | 仅保护 token 自身 payload | 保护整个请求（方法/路径/时间/随机数/Body） |
| 防重放 | 弱（仅靠短 exp，窗口内截获即可重放） | 强（timestamp + nonce 双重限制） |
| 适用场景 | 内部可信服务间身份传递、用户会话 | 外部不可信调用方、Webhook 回调验源 |
| 实现复杂度 | 中（拦截器已落地，见本周交付 1） | 中高（需 Redis 配合维护 nonce） |
| 密钥形态 | 对称 HS256（内部共享），可扩 RSA 对外验签 | 每个 AppKey 一把对称 secret |

两者是**互补而非替代**：外部调用方可以“JWT 声明身份 + HMAC 签名护请求”叠加使用；内部服务间只有 JWT 即可（网络边界可信）。
